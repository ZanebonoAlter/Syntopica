## 2. 结论与处置

- 内容判据（叙事形态、禁项、量级）**全部通过**；形态判据「读完一句完整的话」**不通过**：200 字预算装不下「阶段→驱动→落点→量级」四段，模型稳定写到 250-300 字后被机械截断，读者在泳道趋势区看到半截话。这是「机械截断保护」从兜底变成常态路径。
- 处置（按 5.3 「不合格回改 prompt 而非放宽判据」+ 用户 2026-10-28 裁决）：
  1. prompt 加篇幅硬约束：总长（含标点）≤200 字、必须以句号收尾、写不下压缩/合并阶段；
  2. 解析端 `clampLaneSnapshotRunes`：超限优先在窗口内最后一个句末标点（`。！？…`）收口，标点过早（< 60% 预算）或整段无标点时退回 rune 硬切；
  3. 只改上述两处，**不放宽 200 字口径**、不改 spec 字数区间。
- 复验计划：下个日报日（2026-10-29 凌晨）结算后重跑同一组 SQL——期望「以句末标点收尾」≥ 90%、字数仍 ≤200；合格后把 tasks 5.3 勾选并归档本 change。

### 4.2 复验发现：量级信号近7/上7合计与打印标签错位一天（R-12）

复验中对文中引用的量级数字逐条回算真库，发现 **16 条带量级引用的快照中 11 条**与标称窗口（近7天＝[anchor-6, anchor]、上7天＝[anchor-13, anchor-7]）对不上。

**根因**：`renderLaneMagnitudeSignal` 的 rollup 用 instant 比较（`!c.PeriodDate.Before(nearFrom)`）。`anchor` 经 `NormalizeReportDate` 归一化到**正午 UTC**（12:00），故 `nearFrom`/`prevFrom` 也是正午；而真库 `board_daily_reports.period_date` 是 PG `date` 列，扫出来是**午夜 UTC**（00:00）——窗首日 `00:00 < 12:00` → 被判进前窗。实测口径：标称「近7天＝[10-24,10-30]」实算为 **[10-25,10-30]（6 天）**、标称「上7天＝[10-17,10-23]」实算为 **[10-18,10-24]（7 天）**，且 10-17 当日被两个窗口同时丢弃。

**为何单测没抓到**：测试夹具 `LaneDailyCount{PeriodDate: anchor.AddDate(...)}` 保留 noon 时点，与 anchor 同基 → 窗首日恰好落对；真库形态是 midnight → 触发错位。**夹具形态与真库形态不一致**是漏网直接原因。

**LLM 侧核实**：以真代码路径回算，LLM 对系统给出的（错窗）数字 **16/16 忠实**——即模型没有编数字，是系统给的窗口错了。

**处置**：rollup 比较从 instant 改为**日历日槽位**（与上方每日行同一套 `byDay` 日期串），使「标签区间 = 计入区间」由构造保证；补 PG 形态（midnight 行）回归用例 `TestRenderLaneMagnitudeSignal_PGDateColumnMidnightShape` 锁死窗首/窗末日归属。

**修复后复验**（真库 + 独立 SQL 回算，板块 1980 的 6 条活跃泳道）：

### 4.3 存量快照的处置

修复只影响**后续结算**；修复前已写入的 37 条快照仍带错窗数字（量级引用段），由下个日报日结算自然覆盖自愈（与 `rolling_detail` 存量自愈同一机制，不做回填——与 spec「存量快照兼容」Scenario 一致）。本 change 的 delta spec 含「量级信号随素材注入」Scenario（近7/上7 合计对比由系统统计计算），故该口径修正在本 change 内闭环，不得带着错位口径归档。
