## SQL（AFTER：`articleListColumns` 窄投影）

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT articles.id, articles.feed_id, articles.title, articles.link, articles.image_url, articles.pub_date, articles.author, articles.read, articles.favorite, articles.archived, articles.summary_status, articles.summary_generated_at, articles.firecrawl_status, articles.firecrawl_error, articles.firecrawl_crawled_at, articles.completion_error, articles.created_at,
       feeds.category_id AS category_id,
       (SELECT COUNT(*) FROM article_topic_tags att_cnt WHERE att_cnt.article_id = articles.id) AS tag_count
FROM articles
LEFT JOIN feeds ON articles.feed_id = feeds.id
WHERE articles.archived = false
ORDER BY articles.pub_date DESC
LIMIT 20;
```

## 结论（rows / 循环特征无恶化）

1. **计划形状逐节点一致**：before/after 均为 `Limit → Result → Sort(top-N heapsort) → Hash Left Join(articles ← feeds) → Seq Scan articles + Hash feeds`，唯一差异是各节点的 `width`（1075 → 257，Seq Scan 1059 → 241）。
2. **tag_count 仍是逐行相关子查询，未新增 N+1**：`SubPlan 1` 两次均 `loops=20`（每返回行 1 次），走 `Index Only Scan using idx_article_topic_tags_article_id`，Index Searches 20 / Heap Fetches 4，与 before 完全相同。没有引入任何新的 per-row 查询或 JOIN 展开。
3. **rows 特征不变**：Limit/Sort 返回 20 行、Hash Left Join 输出 2039 行、Seq Scan 过滤 22978 行，前后完全一致（同库同时刻）。
4. **代价改善**：仅 row width 变小（1075 → 257，约 −76%），Sort 内存 65 kB → 35 kB；暖缓存 Execution Time 19.171 ms → 16.117 ms（同量级，无恶化）。体积收益主要来自不再把 `content`/`description`/`firecrawl_content`/`ai_content_summary` 从 TOAST 取出并搬运到应用层。
5. `articles` 表的 Seq Scan 是 2039/25017 活跃行的既有特征（before 相同），非本次引入；如需可另开索引优化项，不属本 change 范围。
