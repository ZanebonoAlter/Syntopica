## 四、真正需要收口的三处缺口

这些是后续规范/门禁变更的建议，**本轮未直接修改规则或门禁**。

### 1. 在已有 ui-design 八节内补“产品职责”，不另造一套文档

- Information Architecture / Interaction Contract：每个动作写明**作用域（全局/当前板块/当前文章等）、主入口、必要快捷入口及为何需要、操作后去向**。全局动作放总览；上下文入口若保留，必须说明并正确表达范围。
- Component Reuse：不只列组件名，还注明**宿主形态（流内/抽屉内/独立浮层）、宽度和滚动归属、关闭/返回/焦点恢复**。复用旧内联组件不等于它会自动变成浮层。
- 图、矩阵、列表之间的替换：分别对账它们传递的**信息语义与用户决策**，包括 identity、similarity、待确认关联；“看上去都是时间线”不是等价依据。
- 复用控件的目的在于主题、密度、焦点、交互一致。**不一刀切禁止原生 HTML**，也不允许仅加边框便宣称完成产品适配；基础组件可内部采用原生语义。

### 2. 修复验收必须复走原故事，不以新按钮存在作为结束

- 计算明细：选文章 → 看组合/辅助标签及描述 → 打开计算 → 当前视口可读可点击 → 返回原文章与筛选。
- 日报：阅读中切板块/日期 → 仍知道当前板块与日期 → 空期/追踪命中/返回路径可理解；在承诺的 1440、1920、2560 CSS 视口核对操作区，而不是只给雷达拍一张 4K 图。
- 编排：不知道术语的用户能发现从哪里开始 → 读事件含义与关联 → 区分相似和同话题延续 → 选择/检查/命名/保存；写入验证用隔离测试数据，本轮不在真库试保存。
- 审查人与实现者的职责分开：实现者提供证据；独立审查从用户任务、位置和作用范围判定是否成立。已批准的原型也可以暴露设计错误，不能成为否定真实问题的理由。

### 3. 分清“证据门禁通过”与“交付合格”

- 本轮改证据前，`ui-verification-trace.sh` 返回：**54 条 pass，52 张点名截图全部在盘**；`review-trace.sh` 返回 8 条合法记录。
- 但前者 major 分支只校验合法条目及点名截图存在，统计 `pass/fail/未覆盖` 后即可退出 0；**不判断已知 fail 是否修复、必验故事是否齐全、截图是否真的展示点击后的结果、合同承诺的视口是否覆盖**。这属于现有留痕门禁的能力边界，不能把退出 0 宣称为产品验收通过。
- 应在归档就绪判定中检查**必验故事的最新结论、失败修复后的复验对应关系、核心未覆盖项的明确处置**；保留失败历史，不通过删条目或缩合同制造全绿。视口以合同为准，截图核对实际尺寸，不只看文件名。
- 主观产品判断仍由评审负责，不能让脚本“识图判断好不好看”。规则改造应单独走流程 change，先保留本次反例，再在后续 major UI 变更中回检，避免每个投诉叠一个专用禁令。

## 五、当前 change 的返工顺序

1. 把原 A-43 撤回为未通过，将本轮问题建账；暂停旧组件清理与完成宣称。
2. 回 requirements 修订产品合同和原型：总览负责全局治理/创建；板块负责本板块内容与治理；文章解释在文章工作面内完成；关系浏览保留可理解的职责；日报切换作为正式操作区设计。
3. 涉及信息架构/主流程/布局模式的修订将审批重置 pending，用户确认修订原型后再继续实现。不要再在右轨、列表末尾和更多菜单补一轮按钮。
