# Design

## D1 为什么先修过期、后拆巨型

两个 spec 都是 700+ 行，天然想拆。但审计给出的事实是：**内容本身有错**。

如果先拆：
- 拆分要求「逐字搬运、零语义变更」的守恒验证。混入内容修正后，守恒验证立刻失效——分不清某条改动是「搬过来」还是「改过」
- 错的数值会被分散到两个文件，读者更难发现矛盾（原来同文件内 R2 与 R11 打架还看得出来，拆开后连打架都看不见）

所以顺序是：**先让 spec 追上代码（本 change），再考虑拆分（另开 change）**。这也符合「一个 change 只做一件事」的纪律。

## D2 只修有 `file:line` 证据的条款

10 条必须修 + 5 条缺写，每条都能指到具体代码行。审计报告里「无法核实」的项（`workshop-board-console` 1 条、`lane-correction-surface` R10 的像素高度）**不动**——没有证据就不改，避免用猜测替换猜测。

判定纪律：
- **代码是唯一真相源**。spec 说 44，代码算出来 48，就以代码为准
- 但代码也要看**时序**：如果 spec 写的是 11-17 定稿的 380/300，而代码 11-02 就写了窄档覆盖，那不是 spec 过期，是 spec 漏记了一个分支 → 修正方向是**补分支**而不是改数值
- 死代码（`BoardLaneEvolution.vue:215-217`）不算证据——它不在渲染路径上，spec 的 MUST NOT 依然成立，只是要在 spec 里注明「存在与条款相悖的死代码，待清理」

## D3 数值类条款的写法：写「约束 + 出处」而不是写「计算结果」

行距这条教训最深：spec 写 `40 + 4 = 44`，看起来精确，但它是**推导结果**。代码一旦改 `MEMBER_BASE_RADIUS` 或加一个 `LABEL_BOX_PAD`，推导就废了，而 readers 不会重算。

修正后的写法要求：
1. 先写**约束**（「节点块高 SHALL ≥ 圆心半径×2 + 标签高度，保证标签框底与下一圆顶不相切」）
2. 再写**当前取值**并标注它是「当前取值、非契约」
3. 指名**唯一出处**（`NODE_BLOCK_H` 常量），读者要改数值就去改常量，不在 spec 里改

这样 spec 描述的是「不许重叠」这个不变量，而不是一个会漂移的数字。

## D4 三视图这条是上一轮自伤，先说清怎么防

`merge-lane-ops-specs` 把 archive 视图并入 `workshop-board-console` 时，只 ADD 了 8 条新 Requirement，**没有回头检查同文件里的旧条款**（R14 说「两个同级视图」）。这是「新增条款与既有条款矛盾」的典型。

同类风险的检查方法（本次已用）：
- 改一个 spec 的「构成类」事实（有几个视图 / 有几个块 / 有几档）时，`grep` 该数字在该文件的所有出现
- 本 change 的 R3（两视图→三视图）与 R6（四块→五块，5 处）都是这么找出来的

## D5 跨族重复条款为什么不在这里修

7 条与 `workshop-lane-compose` / `lane-ops` 逐字重复（`高度贴合容器`、`横向吸顶标签列`、`缩放滚动外壳`、`窄屏门限`、`批内相对归一`、`首义读端点零写副作用`）。

修它们要决定「归谁」——那是族边界问题，不是过期问题。混进来会让本 change 的验证目标（spec 追上代码）变模糊。已登记到「跨族引用清扫」批次。

## D6 验证方式

不是跑测试，是**逐条对证据**：

| 验证点 | 方法 |
|---|---|
| 数值类（行距、宽度、步长） | 重跑审计报告的证据命令，确认新写的数值与代码一致 |
| 枚举类（视图数、块数、排序档） | `grep` 代码里的枚举定义，确认 spec 列举 = 代码列举 |
| 缺写类 | 每条新增条款必须带 `file:line` |
| 改动范围 | `git diff --stat` 只应触及 2 个 spec 文件 + 本 change 目录 |
| 未触碰 | 两个 spec 的 Requirement 总数不变（33 / 19），只改内容不增删条数 |
