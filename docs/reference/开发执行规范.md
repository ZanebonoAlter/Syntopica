**业务约束归属**（放错层会导致权威散落、规范与流程混在一起）：

| 约束类型 | 归属 |
| --------- | ------ |

**防孤立约束**：`standard/` 下每个文档必须被对应 `AGENTS.md` 或 `standard/README.md` 引用；`scripts/check-standards.sh`（L1）归档前校验（见 §11.4）。

## 0.6 openspec change 标准编排流程（主线程调度模型）

> **准入总则（openspec 优先）**：凡涉及代码 / 功能 / 接口 / 数据模型的改动，**默认必须先开 openspec change**（proposal → apply → archive），用 change 管住设计、测试、文档溯源。仅在以下**豁免清单**内可不单独开 change，但仍走 §2 用例先行 + §4.1/§5.1 门禁：
> - 纯文档修订（typo / 措辞 / 补链，不改行为语义）
> - 单文件小修（注释 / 日志文案 / 不涉逻辑的格式，≤10 行）
> - 紧急 hotfix（生产故障先修，**事后 24h 内补 change 归档**）
> - 纯配置 / SQL 迁移脚本（沿用 §2 豁免，但需人工验证 + 记录）
>
> 不确定是否豁免？**默认开 change**。「开 change 太重」不是绕过理由——编排六步可按下方「何时偏离」裁剪，但 change 本身必须存在（proposal + archive 溯源）。

> **主线程只做调度与进度跟踪，重活派发子线程**。子线程模型选型见根 `AGENTS.md`「子线程派发参考」。
>
> **UI 设计工作流（syntopica-ui schema，make-ui-design-first-class）**：默认 schema 已切 `syntopica-ui`（`openspec/config.yaml`），新 change 的 artifact 顺序为 `proposal → ui-design → specs/design → tasks`，proposal 头部 MUST 同时声明 `<!-- complexity: ... -->` 与 `<!-- ui-impact: none|minor|major -->`（两维度正交）。`ui-design.md` 按档位缩放：none=最小 N/A、minor=复用/状态契约、major=完整八节+`ui-prototype/` 可丢弃原型，审批 marker `<!-- ui-approval: pending|approved -->` **只有用户对话明确确认后才可改 approved**。major 且 pending 时 apply 停在 requirements 档展示原型，`ui-design-gate` 扩展硬拦截实现派发/项目代码写入（逃生口 `UI_DESIGN_GATE_BYPASS=1` 留痕）；rollout 前的旧 spec-driven change 不硬阻断，触及前端时每 session/change 提醒一次。判据与布局契约见 [`standard/frontend/layout.md`](standard/frontend/layout.md)。

### 编排六步

> **业务域声明（propose 产物，@constraint-domain-declaration）**：proposal.md 头部写 `<!-- constraint-domains: 域名, ... -->`（域名=flow 文档 basename，如 `daily-report`），显式声明本 change 涉及的业务域——constraint-injection 据此注入对应「业务约束与不变量」节；不涉业务域（纯工具链/纯文档）可不写，apply 时 widget 提示「无域声明」属预期。实现期范围漂移（临时改到未声明域的代码）由 flow 文档头部 `doc-impact-applies` 标签的编辑路径 JIT 命中兜底。
>
> **文档新增/修订**：碰 `docs/reference/` 下任何文档的新增或结构性修订，先读 [`standard/shared/doc-authoring.md`](standard/shared/doc-authoring.md)（目录职责、三种头部注释语法、flow 模板、注册点 checklist 与门禁拦截点）。

| 步 | 执行者 | 动作 | 产出 |
| ---- | -------- | ------ | ------ |
| 1 | 主线程 | 读 change 制品 + 本规范相关章节 + 受影响代码建立上下文；**跑 `bash scripts/doc-impact.sh suggest` 做文档域预勾选**。约束上下文（业务规范 what：flow「业务约束与不变量」节 + 执行规范 how：standard「## Requirements」节）由 constraint-injection extension 每 turn 自动注入 system prompt，无需手动跑注入命令。调研驱动型 change：产出 `research.md`（含关键代码摘录+源路径+快照日期+采纳决策表，见 `docs/research/README.md`） | 变更上下文 + 文档域预勾选 +（如适用）research.md |
| 2 | 主线程 | 按 opsx-apply 约束编写实现计划（**含 Scenario→测试文件映射表雏形**，格式按 `scenario-trace-gate` 约定：验证节内 `| Scenario | 测试文件 |` 表，测试文件为仓库根相对路径或「人工…」说明）；**确认 suggest 预勾选后，以 `<!-- doc-impact: 域列表 -->` 机器可读注释写入 tasks.md 文档节** | 实现计划（含映射表）+ doc-impact 声明 |
| 3 | 子线程 | 执行计划（按根 `AGENTS.md` 模型表选型派发）。**前置：复杂逻辑（状态机≥3状态/算法/多模块协议）先派子线程枚举白盒用例（分支表/边界值清单落 change 目录，断言判据主线程定）**；**UI major change 须已获用户原型批准（ui-approval: approved）才可派实现子线程**（ui-design-gate 硬门禁）；测试代码与实现顺序解绑（§2） | （复杂档：白盒用例文档）+ 代码 + 测试 |
| 4 | 子线程/主 | 人工聚焦 review（见下「review 执行要点」）。⚠️ `ocr`/open-code-review 在本仓库因路径幻觉致 `file_read failed` 连环超时、零有效输出**已弃用**，详见 [`ocr 弃用记录`](../experience/ocr-review-pitfalls.md) | review 意见 + 修复 |
| 5 | 子线程 | 验收门禁：门禁命令(§4.1/§5.1) + `check-standards`(§11.4) + 文档更新(含 §12.2 变更溯源) + 集成测试(§6) | 全绿 |
| 6 | 主线程 | 全程调度 + 进度跟踪（使用 TODO.md / 本地计划文件），不亲自写实现代码 | 进度可见 |

### commit 与归档解耦（coordinate-concurrent-changes）

并发 change 共享工作树，归档验证不得对着「多个 change 混合脏树」跑：

- **门禁绿即主体 commit**：主体实现完成且增量门禁全绿 + 影响包测试通过后，先做主体 commit（按归属地图 `git add` 本 change 文件），**不等归档**；归档另起收尾 commit（spec 同步 + flow 溯源）。实战验证发现问题的修复以 fixup commit 追加（可 revert，比树上脏文件丢弃可控）。
- **挂起验证不受影响**：harness 类 change 挂 active 状态等其他 change 执行中实战验证——commit 不改变磁盘文件，运行时行为照旧；挂的是 openspec 流程状态，不是 git 脏状态。
- **拆 commit 看归属地图**：`bash scripts/concurrency-status.sh <change>` 人读态势（活跃清单/脏文件归属/近期验证）；同文件多 change 触碰会带冲突标记，需人工确认。
- **态劳拉取挂点**：主线程步骤 3 派发前跑一次 `concurrency-status.sh`（错峰重命令/预判冲突文件）；归档前 spec-gate 检查⑤'自动检查（warn 不 block）。态劳数据不进 system prompt（时变内容破坏前缀缓存），仅以命令输出形态出现。

### 何时偏离

- **纯文档 change**：跳过步骤 3 代码实现与步骤 4 review，步骤 5 走 §11.3 grep 一致性校验，其余不变
- **单文件小修**：步骤 2 计划可极简，但仍须走 review + 门禁，不得跳步
- **疑难/架构级**：步骤 1 上下文建立加重，必要时主线程亲自做步骤 2 计划

### review 执行要点（步骤4，子线程聚焦 review）

ocr 弃用后走**子进程聚焦 review**：

1. **精读高风险文件**（挑 5-8 个，不逐行读全部）：并发/缓存（`sync.Once`/`sync.Mutex`/全局单例查「首次失败是否被永久缓存」）、错误处理（被忽略的 error 返回值是否有 nil 解引用风险）、raw SQL（`.Raw()`/`.Exec()` 是否参数化 `?` 占位符）、agent loop/状态机（去重/上限/不变式防御是否齐全）、handler（`:id` 取出的资源是否属于路径 `:xxxId`，防 IDOR）、事务/竞态（read-then-write 是否原子，应用 `clause.OnConflict` 或事务+锁）
2. **`grep` 全包验证关键不变量**：把 change 声明的不变量转成 grep 命令跨改动包验证（如 `grep -rn 'UpsertX\|X{' service/` 确认某路径不调写操作）
3. **按 High/Medium/Low 分类汇报**：High（bug/安全/清晰错误）必修；Medium（合理但依赖上下文）选修；Low（误报）静默丢弃（ocr/open-code-review 本仓库因路径幻觉零产出，已弃用）

### 收到 review 意见后（author 纪律，加载技能 `receiving-code-review`）

- **先验证再改，禁阿谀**：不说「你说得对／好建议／谢谢」，直接改并说明改了什么（Actions > words）；验证前不实现
- **不清楚全停**：有条目没看懂就停下来问，不要先改清楚的（条目可能相关，部分理解=错误实现）
- **YAGNI 检查**：意见要你「正经实现」时，先 grep 实际调用，没人用就删而不是加
- **该 push back 就 push back**：意见在本代码库不成立/破坏现有/与架构决定冲突——用技术理由反驳（引用工作测试或代码），架构级拉用户；外部或自动 review 工具的意见同样先怀疑、验证再定
- **自己 push back 错了**：事实陈述纠正，不长篇道歉

### 主线程纪律

主线程只调度不写实现代码（除纯文档/单行修）；用 TODO.md 或本地计划文件跟踪进度；子线程返回后**必须核验**实际改动。

### 子线程并行派发（run_in_background）

步骤 3 派发时，**无依赖关系的任务组用 Agent 工具的 `run_in_background` 后台派发**，多个独立组可同时派，主线程不得阻塞干等（2026-08-20 会话分析：纯「派发→阻塞干等→验收」串行模式累计 ~40h 纯等待，引以为戒）。存在并发 change 时，派发前跑一次 `bash scripts/concurrency-status.sh`（见 §0.6「commit 与归档解耦」）——树上若有归属其他 active change 的文件，重命令（全量 lint/build）可考虑错峰，避免对同一棵混合树重复跑。

| 要点 | 做法 |
| ------ | ------ |
| 并行条件 | 任务组间无数据/产物依赖（如两个不同 domain 的实现、文档起草 vs 后端任务） |
| 等待期 | 主线程不闲着：做验收准备（预跑门禁命令）、起草文档、或串行做只能主线程干的活（调度 / review 计划） |
| 收口 | 全部用 `get_subagent_result` 统一逐个验收；验收失败的 `steer` 重定向或 kill 后重派 |
| 红线 | 存在数据/产物依赖的任务**必须串行**：design 未完成不得派实现任务；同文件/同模块改动**不得并行派两个 agent**（写冲突 + review 混淆） |

## 1. 任务拆解规范

apply 启动时将 proposal 垂直切片为 tasks.md 可独立交付子任务；每个子任务含验收标准 + 关联 checkbox；配了 issue tracker 的同步建 issue。

## 2. 实现纪律 — 用例先行

> 用例设计前置到 specs 阶段，测试代码与实现的编写顺序解绑（可先可后可交织）；测试失败难定位加载技能 `systematic-debugging`（四阶段根因调查，未确认根因前不得乱改）。（规则演进：2026-08 前为严格 TDD red-green，amend-dev-workflow 改用例先行——agent 工作流下「先看到失败」的两轮往返 token 成本高且实现中途调整即返工；想清楚测什么的「设计前置」不放松，放松的只是「代码先跑红」仪式。）

**铁律：没有用例设计，不动手写实现。** 用例设计的家：spec.md 的 Scenario（WHEN/THEN）即黑盒行为用例。

> 用例设计标准（测试单元=一个 Requirement+其 Scenario、四问句：节拍/变体/层选择/效果核对、验收措辞黑名单）见 [`standard/shared/test-design.md`](standard/shared/test-design.md)——写 specs/tasks/测试代码时由 constraint-injection JIT 自动注入摘要。

| 场景 | 要求 |
| ---- | ---- |
| 新增模块 / 核心逻辑变更 | specs 阶段完成 Scenario 用例设计；复杂逻辑另出白盒用例文档（见下） |
| 复杂逻辑（状态机≥3状态循环 / 算法 / 多模块交互协议） | 派子线程枚举白盒用例（分支表/边界值清单）落 change 目录；**断言判据（什么算对）主线程定，子线程只做机械枚举** |
| Bug 修复 | **先写复现测试再修代码（不可豁免）**——先复现才能证明修的是这个 bug |
| 现有代码小幅修改 | 至少补充回归测试 |
| 纯配置 / SQL 迁移脚本 | 豁免（但需人工验证） |

**测试代码与实现顺序解绑**：同 change 落地即可，无需证明「测试先于实现」或「曾看到失败」；归档时 tasks.md 验证节列 Scenario→测试文件映射，未映射的 Scenario 视为未覆盖。

**复杂度声明制（proposal 头机器可读声明）**：新 change 的 proposal.md 头部 MUST 携带 `<!-- complexity: complex -->` 或 `<!-- complexity: simple -->`（与 `constraint-domains` 同款 HTML 注释惯例，独立成行置于头部）。判定：状态机≥3状态循环 / 算法逻辑 / 多模块交互协议任一命中 → complex，其余 simple——复杂度是设计阶段判断（propose 时点），不是实现事后归类。机器执行（不靠自觉）：声明 complex + 缺 test-cases*.md → entry-gate 在 implementation 档动工首回合 steer 提醒、spec-gate ⑤a 归档 warn 强违例；声明 simple / 未声明但任务行命中兜底关键词（算法/状态机/解析/协议）→ 反向质询（改声明或补文档）；词表不扩容（主信号=声明）。openspec 官方 skill（new-change/propose/continue）不植入本仓库定制项，声明义务以本节为准。

**红旗（遇到即停）**：动手前 specs 无 Scenario / proposal 缺复杂度声明 / 复杂档缺白盒用例文档 / bug 修复无复现测试 / 归档验证节无 Scenario→测试映射——停下补齐再继续。

## 3. 复杂设计验证（先脑暴 → 后原型）

设计边界不清 / 需求多解 / 交互形态未定时，先加载技能 `brainstorming` 做纯对话探索（澄清意图、列方案、定取舍，**不出代码**），收敛后再进实现。

涉及状态机（≥3 状态循环流转）/算法逻辑/多模块交互协议（API 契约/事件总线）**必须先做可丢弃原型**：输出方案对比+选型理由+风险点入 `openspec/changes/<name>/`，确认后销毁再进实现（原型阶段的白盒用例枚举可与此并行，见 §2）。

> brainstorming 是「先聊清楚」（轻、纯对话），原型是「用代码验证」（重、出代码）——不要跳过 brainstorming 直接堆原型。

### 3.1 UI 原型通道（与复杂逻辑原型正交）

UI 影响由 proposal 的 `<!-- ui-impact: none|minor|major -->` 独立声明，与 `complexity` **两维度正交**——治理面板可以逻辑简单但 UI major，解析器重写可以逻辑复杂但 UI none。两条原型通道各走各的，互不替代：

| 通道 | 触发 | 制品 | 确认方式 |
| ---- | ---- | ---- | ---- |
| 复杂逻辑原型 | `complexity: complex`（状态机/算法/协议） | 方案对比+选型理由入 change 目录，确认后销毁 | 用户对话确认，无机器 marker |
| UI 原型 | `ui-impact: major`（新页面/面板/弹窗/导航/多步/信息架构/布局模式） | `ui-design.md` 八节合同 + `ui-prototype/` 静态原型 + `<!-- ui-approval: pending|approved -->` | **用户对话明确确认后才可改 approved**；信息架构/主流程/布局模式修订后 MUST 重置 pending |

UI major 且 approval=pending 时：propose/continue 停在 requirements 档展示原型，apply 前置检查与 `ui-design-gate` 扩展（implementation 档）双重拦截实现派发与项目代码写入（当前 change 的 ui-design.md / ui-prototype/** 修复不受限）。布局选型（reader=760 / contained=1120 / workspace / split、dialog sm/md/lg/xl）权威见 [`standard/frontend/layout.md`](standard/frontend/layout.md)。

## 4. 后端执行规范（Go + Gin + GORM）

### 4.0 前置条件

apply 启动时检测，缺失作为首个子任务补齐：`go vet ./...`、`golangci-lint run ./...`、`go test ./...`、`go build ./...` 可正常执行（未装 golangci-lint：`go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@latest`）。

### 4.1 质量门禁

```bash
cd backend-go
golangci-lint run ./... && go vet ./... && go test ./... && go build ./...
```

| 工具 | 用途 |
| ---- | ---- |
| `golangci-lint` | 静态分析（staticcheck/revive/gosec 等） |
| `go vet` | Go 官方静态检查 |
| `go test` | 单元测试执行 |
| `go build` | 编译检查 |

**门禁分层**：约束注入（[`.pi/extensions/constraint-injection.ts`](../../../.pi/extensions/constraint-injection.ts) 在 `before_agent_start` 每 turn 自动注入：flow「业务约束与不变量」节按关键词命中、standard 文档按编辑路径 JIT 命中——注入管"知道"）→ 增量（pi extension 每回合 `turn_end`，**会话内增量路由**：仅本回合相对快照新增/变化的路径命中对应侧才跑——后端命中跑 `golangci-lint`+`go vet`+`go build` 并经 [`scripts/change-scope.sh`](../../../scripts/change-scope.sh) 路径映射自动跑影响包 `go test -short ./internal/<domain>/...`（`-short` 下 DB 集成测试自动 skip，无需 Docker），前端命中才跑 `pnpm lint`；会话前残留脏文件不触发，上回合失败未转绿粘性重跑；[`.pi/extensions/quality-gate.ts`](../../../.pi/extensions/quality-gate.ts)，harness-observability-fixes 引入）→ 日常验证（agent 手动跑完整影响包测试 `bash scripts/change-scope.sh` 看命令清单 / `pnpm test:unit`）→ 归档全量（§11：`go test ./...`+`go build ./...` / `pnpm build`+`nuxi typecheck`）。增量不跑前端 typecheck/build/test（需 cmd.exe，bash hook 脆弱），完整门禁由 §11 兜底。真 Claude Code/Codex 无 pi extension，需手动跑增量门禁。

**影响包机械判定（change-scope）**：[`scripts/change-scope.sh`](../../../scripts/change-scope.sh)（add-change-scope 引入，思路源自 deepseek-harness）按 git diff 改动路径 + 目录自动发现的三档映射输出最小验证命令（domain 档 `go test -short ./internal/<domain>/...` / platform 档全量 vet / 骨架档 build+vet / 前端 lint；未命中路径报「无法判定」绝不猜测）。`--json` 供 quality-gate 消费。新增 domain 目录零维护（运行时发现）。「测试只跑影响包」以此脚本为准，不再靠自觉。

**派发额度门禁**：除质量门禁外，[`.pi/extensions/quota-gate.ts`](../../../.pi/extensions/quota-gate.ts) 在 `tool_call` 拦截 `Agent` 工具调用做供应商额度预检（GLM/Kimi 查 5h/周窗口百分比、DeepSeek 查余额，opencode-go 无 API 放行），额度不足 block 并把中文 reason 喂回主线程换模型重试；查询失败 fail-open 不阻断（fail-open 放行落 custom_message 留痕，2026-08-20 起）。阈值/缓存 TTL 走环境变量（`QUOTA_GATE_WINDOW_PCT`/`QUOTA_GATE_MIN_BALANCE`/`QUOTA_GATE_TTL_MS`），设计见 openspec change `agent-quota-gate`。

**归档硬门禁（spec-gate）**：[`.pi/extensions/spec-gate.ts`](../../../.pi/extensions/spec-gate.ts) 在 `tool_call` 拦截 bash 里的 `openspec archive` 命令，放行前强制四项检查：① `doc-impact.sh verify <change-dir>` 退出码 0（反向启发式双轨输入：事实库存在该 change 的 `edit.map` 归属集合且非空时只扫归属集合，其他 active change 的脏文件不再干扰；无记录/空/库不可用回退全树 git diff 且命中仅提示不判 FAIL；两轨统一剔除工具自管文件与共享文档黑名单——fix-doc-impact-misattribution，跨 change 误报源消失后 `doc-impact-excuse` 退役，既有注释读取兼容）；② `check-standards.sh --change <change>` 无失败（A-E/G-H 仍全仓检查，**F 段只对账归档目标**）；③ tasks.md 尾三节（测试/文档/验证，各自独立匹配）+ `<!-- doc-impact:` 声明标记存在；④ `scenario-trace.sh <change-dir>` 退出码 0（Scenario→测试映射对账，scenario-test-mapping-gate 引入，格式见 `openspec/specs/scenario-trace-gate`）。任一失败 block + 中文 reason（含修复指引）；豁免通道 `--force` / `SPEC_GATE_BYPASS=1`（记 warning 留痕不静默）；开关 `SPEC_GATE_ENABLE`（默认开）/`SPEC_GATE_TIMEOUT_MS`（默认 60s）。①②④均不跑测试（§11.1 条件 1 仍归 agent 手动）。另：**检查⑤'（warn 级不 block，coordinate-concurrent-changes）**：`concurrency-status.sh --check <change>` exit 2（树上存在归属其他 active change 的未 commit 文件）→ steer 提醒拆 commit/协调收口 + `policy.decision(warn, concurrent-dirty-tree)` 记账；exit 3（冷启动全无归属/库不可用）零输出。

**全量测试软守卫（test-scope-guard）**：[`.pi/extensions/test-scope-guard.ts`](../../../.pi/extensions/test-scope-guard.ts) 在非归档语境检测到全量 `go test ./...` 时发软提醒（notify，不 block），归档语境（命令或近期上下文含 归档/§11/archive/验证节/pre-push，或命令带 `# archive-gate` 注释）直接放行；`TEST_SCOPE_GUARD=soft|hard|off` 默认 soft（hard 才 block）。

**门禁裁决记账（policy.decision）**：spec-gate / quota-gate / test-scope-guard 的显著裁决（`block` / `warn` / `bypass` / `fail-open` 四种 action）统一追加 `policy.decision` 事件到事实库（保留 30 天，harden-harness-policy-and-spill 引入），普通成功放行零记录、quality-gate/entry-gate 继续只用 `gate.check` 不双写；记账经共享 helper `.pi/extensions/lib/policy-decision.ts` 收敛 payload（reasonCode 稳定 kebab-case 枚举、target 仅 change/provider 短摘要，禁合命令/密钥/响应正文），写入失败严格旁路不影响裁决。定期健康复盘查法见 skill `harness-facts` 查询配方 §7/§8。

### 5.3 端到端验证规范（opencli 主力 + glm-5.3-flash 视图验证）

前端单测验证组件逻辑；端到端验证补「数据 + 状态 + DOM 运行时组合对不对」这层缺口。**工具按验证目的分流**（实测结论：opencli 复用真实浏览器持久状态，彻底消灭 playwright 每次起干净实例要跟首屏引导弹窗搏斗的痛点）：

| 验证目的 | 工具 / 执行者 | 理由 |
| -------- | ------------ | ---- |
| **交互流程验证**（多步导航、点击、tab/面板激活、数据渲染对不对） | **opencli**（主线或子代理 bash 调 `opencli browser *`） | 驱动真实 Chrome 复用持久状态（引导已关/登录态/localStorage），消灭首屏弹窗拦截；numeric ref + `match_level`（exact/stable/reidentified）抗选择器漂移，错误率远低于 CSS selector |
| **视图/视觉验证**（截图看布局/样式/响应式对不对） | 派 **zai-coding-cn/glm-5.3-flash** 子代理截图判断 | 主观视觉/审美判断，视觉模型优于通用模型（用户约定 2026-09，替代 kimi-coding/k3） |
| **页面骨架/响应式 smoke**（CI 可重复、需纯净隔离） | Playwright `tests/e2e/*.spec.ts`（仅极稳定 smoke） | 独立实例无浏览器依赖，适合 CI；业务交互回归脆弱**不堆** |

**opencli 前置**：`opencli doctor` 绿（daemon + Chrome 扩展已连）→ `OPENCLI_WINDOW=background` 不抢用户当前 tab → 本地 dev server 一律用 `http://localhost:<port>`（WSL2 localhost 镜像直达，勿用局域网 IP）。

**铁律**：`click` 触发 Vue 状态变更后，DOM 在 nextTick 才重渲染——**必须 `opencli browser <sess> wait time 1~2`（或 `wait selector`）后再 `state`/`get`**，同步读得旧值=假阴性（头号坑）。

**派发要点**：opencli 交互验证给子代理「导航路径 + 断言脚本」，断言写成代码（读 `state`/`get text` 原始值，python/grep 机械判定），**不让模型主观判断对错**；导航路径见 [`architecture/ui-navigation.md`](architecture/ui-navigation.md)，避坑全貌与派发模板见 skill `ui-verify`（opencli 命令用法看官方 skill `opencli-browser`）。

**major UI 双层验收（对照已批准基线，make-ui-design-first-class）**：声明 `ui-impact: major` 的 change 完成验收 = ① opencli 主交互链路机械断言 + ② **1440×900 与 1920×1080 两档视口**的视觉子代理检查（布局符合 ui-design.md 所选 layout mode、无横向溢出；窄屏支持另加）+ ③ 实现与已批准原型的差异说明（回写 ui-design.md Acceptance 节，重大差异需重新审批）。只有组件单测不算完成 major UI 验收（归档门禁检查④'机器拦截，spec-gate 记 `ui-design-gate` block `ui-verification-missing`）。minor 至少映射到组件测试/opencli/人工验证之一。验收分流细则见 skill `ui-verify` 与 [`standard/frontend/layout.md`](standard/frontend/layout.md)。

**前端验收四维度（split-board-upgrade-directions 补修确立，2026-09-07）**：前端验收按维度对账，缺维度=验收不完整。上面的工具分流表回答「用什么工具」，本表回答「验哪个维度、验到什么程度」：

| 维度 | 验什么 | 最低要求 | 手段 |
| ---- | ---- | ---- | ---- |
| 功能正确性 | 元素存在、交互链路、参数正确 | minor/major 必测 | 组件单测（data-testid 断言）+ opencli 机械断言（major 主链路） |
| **展示合理性** | 布局位置、层级（遮罩/z-index/居中）、响应式、无破版 | minor：浮层/弹窗/布局变更处至少 1 个机械锚；major：机械锚 + 双视口视觉子代理目检 | ① 机械锚单测（浮层类组件：样式规则锚 + Teleport 挂载锚，模板见 skill `ui-verify`）② 浏览器层 computed style 断言 ③ glm-5.3-flash 视觉目检 |
| 制品完整性 | ui-impact 声明、ui-design.md、原型审批 | 门禁机器拦截 | ui-design-gate / spec-gate 检查④' |
| 证据存在性 | 勾选的任务有实物对得上 | 声明「截图留证」的任务，截图 MUST 落 `openspec/changes/<name>/ui-verification/`；tasks 勾了 [x] 但目录无对应文件 = 空转 | 归档前人工对账目录实物 |

## 7. 架构体检

### 7.1 codegraph 代码图检查（强制）

每个子任务完成后必须执行：

1. `codegraph impact <修改的符号>` → 影响分析，确认波及面无 HIGH/CRITICAL 风险被忽略
2. `codegraph affected <改动的源文件>` → 变更检测，确认受影响测试文件范围符合预期

- `impact` 返回 HIGH/CRITICAL 风险必须暂停向用户报告，不得忽略
- **已知局限 1**：codegraph 无法追踪 Gin handler 的 `group.GET/POST(..., fn)` 注册模式，会把仅由路由注册引用的 handler 误报为「无调用者」（约 26 个误报）。删除 Gin handler 前必须用 `grep` 二次校验其是否被路由注册引用，避免误删
- **已知局限 2·顺传导链深查**：`codegraph impact` 只显示**直接调用面**，看不到跨层/跨域的**隐式传导**（如「改截断排序 → 经 LLM 聚类输入 → 打散 topic 锚定」）。若改动处于某条传导链上（查 [`coupling-map.md`](architecture/coupling-map.md)），必须人工顺链推导下游影响，不能只看到直接 impact 就收工。踩到/分析出新的跨功能传导耦合，**必须往 `coupling-map.md` 补一条**（含守卫测试）

### 7.2 架构合理性检查

退一步做全局审视（zoom-out，不再挂技能）：新增模块与现有系统耦合度、是否引入循环依赖、是否符合现有分层（后端 `internal/{reader,tagmanagement,topicgraph,admin}` + `internal/platform/*`；前端 Vue 3 Composition API + Pinia）。耦合过高则暂停并提出重构建议。

## 8. 变更控制

> apply 阶段允许按需调整 proposal/spec/design/tasks 范围，但调整须**留痕可溯**。

| 程度 | 判据 | 处理 | 与 plan mode 关系 |
| ---- | ---- | ---- | ----------------- |
| 局部澄清/纠错 | 单个 task 实现细节调整、字段名修正、补充边界条件 | 就地改 spec/design/tasks + tasks.md 留痕 | 不需重新 ExitPlanMode |
| 范围扩展 | 新增 1-2 个 task、补遗漏的需求场景 | 就地改 + tasks.md 留痕 + 通知用户 | 不需重新批准，但回复中告知范围扩大 |
| 中等重构 | 重写 >3 个 task、换核心数据结构、改 API 契约形状 | 就地改 + tasks.md 留痕 + **重新 ExitPlanMode 获用户批准** | 需重新批准（plan 核心假设变了） |
| 方向性变更 | 换技术栈、改核心目标、推翻 proposal 根本目标 | **新开 change** 或 archive 旧的 | 新 change 走完整 propose→apply |

> 用户对范围变化有知情权：哪怕就地改，只要扩展了批准范围（新增 task、改了对外契约），必须在回复里明说。

- 禁止在代码注释写「TODO：后续优化」却不记录到 tasks.md
- 归档前禁止跳过 §11 归档门禁；验证节命令未实测通过的 change 不得 archive

## 11. 归档门禁（Archive Gate）

> 提交前门禁（§4.1/§5.1）覆盖代码质量；归档门禁覆盖「代码↔文档一致性 + 验证可复现」。

### 11.1 归档前置五条件（缺一不可）

> **声称完成前的铁律**（加载技能 `verification-before-completion`）：必须实际跑验证命令并**亲眼确认输出**——不得「看没报错就说过」「命令没跑就说跑过」「上次过了这次肯定过」。归档门禁就是这道理的最后一道关。

1. **测试通过**：§4.1（后端）/ §5.1（前端）/ §6（集成）门禁命令实测通过；纯文档 change 豁免代码测试，但必须在「验证」节附 grep 一致性校验（幽灵路径/调度器/命令、版本号、旧包名零残留）
2. **文档同步**：§9 产出物清单全部勾选，`docs/reference/` 已反映新代码状态
3. **验证可复现**：tasks.md「验证」节（见 §11.2）每条命令实测零失败
4. **Scenario 映射对账**：`bash scripts/scenario-trace.sh openspec/changes/<name>` 退出码 0——delta specs 中每个 ADDED/MODIFIED/RENAMED 的 Scenario 在「验证」节映射表（`| Scenario | 测试文件 |`）有对应行且映射的测试文件真实存在；无自动化测试的 Scenario 显式映射为「人工…」留痕；无 delta Scenario 的 change 直接通过（spec-gate 检查④机器强制，格式约定见 `openspec/specs/scenario-trace-gate`）
5. **UI 验收证据（新 schema change，spec-gate 检查④'）**：按 `ui-design.md` 影响等级对账——major 须 `ui-approval: approved` + 原型存在 + tasks 验证节含 opencli 主链路与 1440×900/1920×1080 双视口证据 + ui-design.md 差异说明；minor 须验收映射（组件测试/opencli/人工至少其一）；none 须 N/A 一致性。任一缺项阻断归档（记 `policy=ui-design-gate` block `ui-verification-missing`）；旧 spec-driven change 零检查不硬阻断；`--force`/`SPEC_GATE_BYPASS=1` 豁免仍留痕

### 11.2 tasks.md 验证节强制结构

每个 change 的 tasks.md **必须**以三个固定尾节收尾：

- `## N. 测试` — 本次 change 影响的测试命令（后端 `go test ./internal/<pkg>`、前端 `pnpm test:unit`）
- `## N+1. 文档` — 需同步更新的 `docs/reference/` 文件。**格式**：第一行机器可读注释 `<!-- doc-impact: 域列表 -->`（apply 第 2 步写入，域列表见 `doc-impact.sh menu` 的 8 选项），下方人读 checkbox 列文件。无文档影响写 `<!-- doc-impact: none(理由) -->`。功能性 change 若触及 `flow/`，须声明将在 §12.2 补「变更溯源」链接（archive 后补）

  > **doc-impact-excuse 豁免**：verify 的「疑似遗漏」启发式（改了某域代码→该声明该域）可能误报——典型：改动语义不属该域（如改 `connect_postgres` 挂 trace 非 schema，不该动 `database.md`）、或工作树有其他 active change 脏文件干扰。确认误报后，在 `<!-- doc-impact: ... -->` 下一行加 `<!-- doc-impact-excuse: domain=理由; ... -->` 豁免。**只豁免「疑似遗漏」，不豁免「声明了未更新」（真没改文档）或「声明的文档不存在」**。

- `## N+2. 验证` — 每条**必须**是「可执行命令 + 期望结果」，禁止只写「已检查」（例：`go test ./internal/admin/scheduler → PASS`）；有 delta Scenario 的 change 须含 `| Scenario | 测试文件 |` 映射表（scenario-trace.sh 归档对账用，格式见 `openspec/specs/scenario-trace-gate`）

### 11.4 归档前自检

执行 `openspec archive` 前：

- 重跑 tasks.md「验证」节全部命令，确认零失败（若归档 skill 仅数复选框，归档前由人/AI 手动补这一步）
- 跑 `bash scripts/doc-impact.sh verify <change-dir>` 对账（域注释 + checkbox 文件两层校验）。启发式误归因收敛（fix-doc-impact-misattribution）：①输入黑名单——工具自管文件（`openspec/changes/**/.openspec.yaml`、`openspec/changes/archive/**`）与仓库级共享文档（`AGENTS.md`、`constraints-index.md` 等）不触发“疑似遗漏”；②回退轨降级——`edit.map` 无归属记录时全树命中仅 stderr 提示（`[提示] 无法归属: <域>（全树回退仅提示）`）不判 FAIL；归属轨命中（会话真实编辑）仍 FAIL
- 跑 `bash scripts/check-standards.sh --change <name>`：A-D 段（代码规范结构/domain 白名单/双主题/防孤立引用）+ **F 段（仅对账目标 change 的 doc-impact verify）** + **G 段（导航层文档死链检查）** 归档前必须零失败；E 段（flow 变更溯源链接）针对 archive 区，归档后校验（见 §12.3）。不带参数的 `bash scripts/check-standards.sh` 保持人工全仓巡检语义，F 段遍历全部 active change。

## 12. 文档流转（Archive 即家 → Flow 反向溯源）

> §11 管 archive **前**门禁；§12 管 archive **后**活文档更新。archive 区是「永久归档家」，靠 `reference/flow/` 反向链接串联。

### 12.1 两段式流转

| 阶段 | 位置 | 责任节点 | 状态 |
| ------ | ------ | ---------- | ------ |
| ① 开发中 | `openspec/changes/<change>/` | propose → apply | 临时，可反复修改 |
| ② 归档（永久家） | `openspec/changes/archive/<date>-<change>/` | `openspec sync` + `openspec archive` | 永久归档，不再搬走 |
| ③ Flow 反向溯源 | `docs/reference/flow/<功能>.md` | archive 后由 change 作者补「变更溯源」行 | 活文档，链接回 archive |

`docs/v1.x/` 里程碑目录**降级为可选**：平时 archive 即终点；发版/做主题合集时才批量收进 `docs/v1.x/changes/`。

### 12.2 变更溯源链接（archive 后强制）

`openspec archive` 完成后，change 作者**必须**在受影响的 `flow/<功能>.md` 尾部「变更溯源」表追加一行链接回 archive 目录，格式如下（「归档位置」列**必须**含 archive 目录全名 `<date>-<change>`，供 `check-standards.sh` E 段校验）：

```markdown
| 日期 | 变更 | 摘要 | 归档位置 |
| 2026-06-14 | scheduler-cron | 定时任务改 cron 驱动 | archive/2026-06-14-scheduler-cron（归档缺失，示例占位） |
```

约定：一个 change 动多个 flow，每个受影响 flow 都补一行；纯文档 change / 不触及任何 flow：豁免（tasks.md「文档」节注明「无 flow 影响」）；链接用相对路径（flow 到 archive：`../../../openspec/changes/archive/<date>-<change>`）。

### 12.3 archive 后校验

补完变更溯源链接后，再跑 `bash scripts/check-standards.sh`，E 段（flow 变更溯源链接）必须零失败。校验范围：新流程生效日（`2026-06-29`）之后的 archive change 必须被某 flow 文档引用；历史存量免校验。**溯源宽限期**（fix-doc-impact-misattribution）：归档未满 `GRACE_DAYS`（默认 3 天，`check-standards.sh` 顶部常量）的 change 免检——§12 本就是“归档后补溯源”流程，宽限窗内的债不 block 其他 change 的归档；超期未溯源仍 FAIL（债由本段催收）。tasks.md 声明「无 flow 影响」的豁免语义不变（宽限期不参与判断）。

### 12.4 流转完整性自检

archive change 已补溯源链接 + `check-standards.sh` A-G 段零失败 + `docs/reference/` 反映新代码状态。
