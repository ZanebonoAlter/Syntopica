## 0.5 文档归属规则（写文档该放哪）

| 写的内容 | 归属目录 |
| --------- | --------- |
| 业务链路怎么跑、状态流转、前后端协作 | `docs/reference/flow/<大功能>.md`（配 mermaid，跨端） |
| 代码怎么写、包结构、双主题、lint/测试配置 | `docs/reference/standard/{frontend,backend}/`（**唯一权威源**；AGENTS.md 只留红线速查 + 深链） |
| 架构定位、骨架、运行时、链路追踪 | `docs/reference/architecture/` |
| 详细设计索引（业务域 → 流程 → 代码入口） | `docs/reference/architecture/map.md` |
| 执行流程 / 门禁 / 归档纪律 | 本文件 |
| 运维（配置、部署） | `docs/reference/configuration.md`、`deployment.md` |
| 出现的问题与复盘经验 | `docs/experience/`、`docs/issues/` |
| 调研快照（外部仓库分析/选型对比，无 change 归属） | `docs/research/<topic>.md`（判据与命名见 `docs/research/README.md`） |
| change 强相关调研（直接驱动某 change 的决策数据） | `openspec/changes/<name>/research.md`（随 change 归档永久留痕） |

**业务约束归属**（放错层会导致权威散落、规范与流程混在一起）：

| 约束类型 | 归属 |
| --------- | ------ |
| 业务不变量（状态机 / 幂等 / 去重 / 限额） | flow 文档「业务约束与不变量」固定节 |
| 跨功能传导耦合 | `docs/reference/architecture/coupling-map.md` |
| 代码写法约束（红线 spec 化） | `docs/reference/standard/`「## Requirements」节；按代码路径经 constraint-injection extension JIT 注入（见 §0.6） |
| 数据 / 测试安全红线 | `docs/reference/standard/backend/testing.md` |

**防孤立约束**：`standard/` 下每个文档必须被对应 `AGENTS.md` 或 `standard/README.md` 引用；`scripts/harness/check-standards.sh`（L1）归档前校验（见 §11.4）。

## 0.6 openspec change 标准编排流程（主线程调度模型）

> **准入总则（openspec 优先）**：凡涉及代码 / 功能 / 接口 / 数据模型的改动，**默认必须先开 openspec change**（proposal → apply → archive），用 change 管住设计、测试、文档溯源。仅在以下**豁免清单**内可不单独开 change，但仍走 §2 用例先行 + §4.1/§5.1 门禁：
> - 纯文档修订（typo / 措辞 / 补链，不改行为语义）
> - 单文件小修（注释 / 日志文案 / 不涉逻辑的格式，≤10 行）
> - 紧急 hotfix（生产故障先修，**事后 24h 内补 change 归档**）
> - 纯配置 / SQL 迁移脚本（沿用 §2 豁免，但需人工验证 + 记录）
>
> 不确定是否豁免？**默认开 change**。「开 change 太重」不是绕过理由——编排六步可按下方「何时偏离」裁剪，但 change 本身必须存在（proposal + archive 溯源）。

> **主线程只做调度与进度跟踪，重活派发子线程**。子线程模型选型见下方「供应商与模型选择」。
>
> **UI 设计工作流（syntopica-ui schema，make-ui-design-first-class）**：默认 schema 已切 `syntopica-ui`（`openspec/config.yaml`），新 change 的 artifact 顺序为 `proposal → ui-design → specs/design → tasks`，proposal 头部 MUST 同时声明 `<!-- complexity: ... -->` 与 `<!-- ui-impact: none|minor|major -->`（两维度正交）。`ui-design.md` 按档位缩放：none=最小 N/A、minor=复用/状态契约、major=完整八节+`ui-prototype/` 可丢弃原型，审批 marker `<!-- ui-approval: pending|approved -->` **只有用户对话明确确认后才可改 approved**。major 且 pending 时 apply 停在 requirements 档展示原型，`ui-design-gate` 扩展硬拦截实现派发/项目代码写入（逃生口 `UI_DESIGN_GATE_BYPASS=1` 留痕）；rollout 前的旧 spec-driven change 不硬阻断，触及前端时每 session/change 提醒一次。判据与布局契约见 [`standard/frontend/layout.md`](standard/frontend/layout.md)。

### 编排六步

> **业务域声明（propose 产物，@constraint-domain-declaration）**：proposal.md 头部写 `<!-- constraint-domains: 域名, ... -->`（域名=flow 文档 basename，如 `daily-report`），显式声明本 change 涉及的业务域——constraint-injection 据此注入对应「业务约束与不变量」节；不涉业务域（纯工具链/纯文档）可不写，apply 时 widget 提示「无域声明」属预期。实现期范围漂移（临时改到未声明域的代码）由 flow 文档头部 `doc-impact-applies` 标签的编辑路径 JIT 命中兜底。
>
> **human-feedback 反馈建账（change 可选制品，add-change-lifecycle-retro）**：收到用户对 change 产物（proposal/design/ui-design/原型/实现/文档）的反馈时记入 change 目录 `human-feedback.md`——条目标题行 `### FB-<N> <日期>【<类型>|<归因>】<标题>`（类型=产品|流程；归因五类封闭 frontend|backend|test-gap|fact-check|process，同一问题多因按根因优先归 fact-check）+ 状态行五值封闭（待处理/处理中/已消化/已转挂/已放弃，只用于建账初始化与归档对账不算指标）。格式契约见 add-change-lifecycle-retro design D7 与 [`standard/shared/doc-authoring.md`](standard/shared/doc-authoring.md) 注册点速查。工具 `scripts/harness/feedback.sh`（menu 词表 / add 建账 / verify 归档对账——archive-readiness 顺带调用，未处置条目提醒不阻断）；计量进 `harness-retro.sh --lifecycle` 第五段（条数/归因分布/未处置数，归因高发层→规范整理去向映射）。
>
> **文档新增/修订**：碰 `docs/reference/` 下任何文档的新增或结构性修订，先读 [`standard/shared/doc-authoring.md`](standard/shared/doc-authoring.md)（目录职责、三种头部注释语法、flow 模板、注册点 checklist 与门禁拦截点）。
>
> **操作允许性变更必盘点 UI 绑定点（propose/design 期）**：改「允不允许」（409 拦截放开/收紧、状态流转门槛）时，MUST 打开该动作函数被绑定的组件模板，读 `@click`/`:disabled`/`v-if` 上下文——允许性的 UI 载体是绑定属性，不在调用链上；受影响组件 MUST 进 proposal Impact。ui-design「入口」节须列触发元素实际状态（disabled 条件/确认方式），「入口不变」不算盘点。教训：fix-provider-delete-route-deadlock 漏看删除按钮 `:disabled`，后端级联解绑在 UI 上点不到（配套测试要求见 [`standard/shared/test-design.md`](standard/shared/test-design.md) 问句③）。
>
> **complex 档 tasks 模板固定含 Review 节（review-task-frontload，review 前移）**：proposal 头部声明 `<!-- complexity: complex -->` 的 change，tasks.md 从建立阶段（propose/new-change/continue 生成 tasks 时）起 MUST 含「Review」节——至少一条任务行（`- [ ]` 开头且含 review/审查），内容为「派子线程聚焦 review（审查制品 + diff），意见按 High/Medium/Low 处置后 review.md 建账」；纯文字类 change 改在 proposal 头部声明 `<!-- review: waived -->` 豁免（同检查⑤词表）。机器判定单一事实源 `scripts/harness/check-tasks-tail.sh`：apply 入口（openspec-apply-change skill 第一步先跑，缺行补上再实现）与归档门禁检查③共用，simple/无声明 change 不受影响。步骤 4 review 因此前移为三道防线：建档时注入（本约定）→ apply 入口检查（skill 约定步）→ 归档门禁③兜底；两份 openspec skill（propose/new-change）已同步该约定。

| 步 | 执行者 | 动作 | 产出 |
| ---- | -------- | ------ | ------ |
| 1 | 主线程 | 读 change 制品 + 本规范相关章节 + 受影响代码建立上下文；**跑 `bash scripts/harness/doc-impact.sh suggest [--change <name>]` 做文档域预勾选**（归属优先：change 名三源解析——显式参数 → `PI_SESSION_ID` 查最新 `mode.set.boundChange` → 空；解析到且归属集合非空时预勾选只吃本 change 的 edit.map 归属，脏文件三桶分列〔本 change/其他 active change/无归属〕不静默过滤；解析不到回退全树 diff 并显式标注，退出码恒 0，attribute-concurrent-gate-noise）。约束上下文（业务规范 what：flow「业务约束与不变量」节 + 执行规范 how：standard「## Requirements」节）由 constraint-injection extension 每 turn 自动注入 system prompt，无需手动跑注入命令。调研驱动型 change：产出 `research.md`（含关键代码摘录+源路径+快照日期+采纳决策表，见 `docs/research/README.md`） | 变更上下文 + 文档域预勾选 +（如适用）research.md |
| 2 | 主线程 | 按 opsx-apply 约束编写实现计划（**含 Scenario→测试文件映射表雏形**，格式按 `scenario-trace-gate` 约定：验证节内 `| Scenario | 测试文件 |` 表，测试文件为仓库根相对路径或「人工…」说明）；**确认 suggest 预勾选后，以 `<!-- doc-impact: 域列表 -->` 机器可读注释写入 tasks.md 文档节** | 实现计划（含映射表）+ doc-impact 声明 |
| 3 | 子线程 | 执行计划（按根 `AGENTS.md` 模型表选型派发）。**前置：复杂逻辑（状态机≥3状态/算法/多模块协议）先派子线程枚举白盒用例（分支表/边界值清单落 change 目录，断言判据主线程定）**；**UI major change 须已获用户原型批准（ui-approval: approved）才可派实现子线程**（ui-design-gate 硬门禁）；测试代码与实现顺序解绑（§2）；**派发前取域红线三步（判域 → 取红线 → 粘 brief）与 brief 模板见下「步骤 3 派发前取域红线」**（红线摘要 MUST 原样粘进派发任务文本） | （复杂档：白盒用例文档）+ 代码 + 测试 |
| 4 | 子线程/主 | 人工聚焦 review（见下「review 执行要点」）。⚠️ `ocr`/open-code-review 在本仓库因路径幻觉致 `file_read failed` 连环超时、零有效输出**已弃用**，详见 [`ocr 弃用记录`](../experience/ocr-review-pitfalls.md)；**做了要留痕（change 目录 review.md 建账），不做要显式豁免（proposal 头部 `<!-- review: waived -->`）——两者皆无归档门禁阻断（add-review-trace-gate）** | review 意见 + 修复 + review.md 建账（或 waived 声明） |
| 5 | 子线程 | 验收门禁：门禁命令(§4.1/§5.1) + `check-standards`(§11.4) + 文档更新(含 §12.2 变更溯源) + 集成测试(§6) | 全绿 |
| 6 | 主线程 | 全程调度 + 进度跟踪（使用 TODO.md / 本地计划文件），不亲自写实现代码 | 进度可见 |

### commit 与归档解耦（coordinate-concurrent-changes）

并发 change 共享工作树，归档验证不得对着「多个 change 混合脏树」跑：

- **门禁绿即主体 commit**：主体实现完成且增量门禁全绿 + 影响包测试通过后，先做主体 commit（按归属地图 `git add` 本 change 文件），**不等归档**；归档另起收尾 commit（spec 同步 + flow 溯源）。实战验证发现问题的修复以 fixup commit 追加（可 revert，比树上脏文件丢弃可控）。
- **挂起验证不受影响**：harness 类 change 挂 active 状态等其他 change 执行中实战验证——commit 不改变磁盘文件，运行时行为照旧；挂的是 openspec 流程状态，不是 git 脏状态。
- **拆 commit 看归属地图**：`bash scripts/harness/concurrency-status.sh <change>` 人读态势（活跃清单/脏文件归属/近期验证）；同文件多 change 触碰会带冲突标记，需人工确认。
- **态劳拉取挂点**：主线程步骤 3 派发前跑一次 `concurrency-status.sh`（错峰重命令/预判冲突文件）；归档前 spec-gate 检查⑤'自动检查（warn 不 block）。态劳数据不进 system prompt（时变内容破坏前缀缓存），仅以命令输出形态出现。

### 何时偏离

- **纯文档 change**：跳过步骤 3 代码实现与步骤 4 review（review 走显式豁免：proposal.md 头部机器可读注释区声明 `<!-- review: waived -->`，理由写在正文；单文件小修不豁免——仍须走 review 不得跳步），步骤 5 走 §11.3 grep 一致性校验，其余不变
- **单文件小修**：步骤 2 计划可极简，但仍须走 review + 门禁，不得跳步
- **疑难/架构级**：步骤 1 上下文建立加重，必要时主线程亲自做步骤 2 计划

### review 执行要点（步骤4，子线程聚焦 review）

ocr 弃用后走**子进程聚焦 review**：

0. **design 落点复核**（新增，design-anchor-tax）：逐条 Decision 核对「落点」与「取舍」两行。落点必须四选一且可解析——仓库文件（全路径或仓库内唯一 basename，带 `:symbol` 时符号须能在文件中检索到）、当前 change `tasks.md` 中存在的任务 id、delta spec 中存在的 Scenario 标题、或「无代码落点：<承接制品>，因为 <理由>」；「见 tasks」「后续补」「待定」等空泛表述与同名 basename 歧义一律按未解析。有结论无承接的决策记 **Medium**，标题写「可删项：D1..Dn（无下游承接）」；流程/文档/审查类决策只要写清承接制品与理由即通过，**不误伤**。
1. **精读高风险文件**（挑 5-8 个，不逐行读全部）：并发/缓存（`sync.Once`/`sync.Mutex`/全局单例查「首次失败是否被永久缓存」）、错误处理（被忽略的 error 返回值是否有 nil 解引用风险）、raw SQL（`.Raw()`/`.Exec()` 是否参数化 `?` 占位符）、agent loop/状态机（去重/上限/不变式防御是否齐全）、handler（`:id` 取出的资源是否属于路径 `:xxxId`，防 IDOR）、事务/竞态（read-then-write 是否原子，应用 `clause.OnConflict` 或事务+锁）
1.5 **迁移/替换型 change 的能力去向复核（capability-parity-review，2026-10-25 投诉复盘）**：凡替换路由/宿主/页面壳、退役 tab/栏位、或让旧组件不再挂载，review MUST 先建立「旧能力去向表」再下结论——每行「旧能力 | 旧入口（文件:行 或组件/事件） | 新承接（路由/组件/动作） | 判定（已迁移 / 主动退役 / 遗漏） | 证据」。判定只能四选一，「遗漏」记 High。旧入口 MUST 用 `git show HEAD:<path>` 或现网旧组件核对真实调用点，MUST NOT 只看新页面是否长得像。同时 MUST 走至少 3 条真人主故事（不是点开面板）：如「无活跃泳道但有日报 → 能读」「归档 → 站内读正文 → 回原日期」「历史格子 → 同日归档」「阅读中切版块/追踪命中」；主故事断链记 High。review 报告 MUST 把「新页面存在」与「旧故事仍可完成」分开写，前者不能抵消后者。

2. **`grep` 全包验证关键不变量**：把 change 声明的不变量转成 grep 命令跨改动包验证（如 `grep -rn 'UpsertX\|X{' service/` 确认某路径不调写操作）。迁移/替换型 change 另须 grep 旧动作的全部调用点（如 `deleteBoard(` / `handleDeleteBoard` / `viewArchive` / `openArticle`），确认新宿主是否真的接上。

3. **按 High/Medium/Low 分类汇报**：High（bug/安全/清晰错误/**用户主故事断链、旧能力不可达且未主动退役**）必修；Medium（合理但依赖上下文）选修；Low（误报）静默丢弃（ocr/open-code-review 本仓库因路径幻觉零产出，已弃用）
4. **建账留痕（add-review-trace-gate，归档门禁强制）**：review 意见落 change 目录 `review.md`（随 change 归档永久保存，不进 events.db）——每条一个条目：标题行 `### R-<N> <YYYY-MM-DD>【High|Medium|Low】<标题>`（编号自 R-1 自增），下一行状态行 `- **状态**：<处置词>`（括号说明可选；五值封闭：待处理/已修复/已采纳/已驳回/误报丢弃）；审了没问题的写显式声明行 `- 审毕无发现（审查范围：<说明>）`。不做 review 的 change（如纯文档）在 proposal.md 头部机器可读注释区声明 `<!-- review: waived -->`（与 ui-impact 同层；waived 占比进 `harness-retro.sh --lifecycle` review 覆盖统计防滥用）。格式契约见 `openspec/specs/review-trace-gate`；归档对账 `bash scripts/harness/review-trace.sh openspec/changes/<name>`（零痕迹/空壳文件均阻断）。归档前 High 条目状态 MUST 为 `已修复/已采纳/已驳回/误报丢弃`，MUST NOT 停留 `待处理/处理中`；未修 High 必须写明承接的新 change 并显式置为 `已驳回（转挂 <change>）`，或由用户明确同意后驳回。Medium 未修同样写清承接/驳回理由；不得用「审查完成」替代「问题已处置」。

### 收到 review 意见后（author 纪律，加载技能 `receiving-code-review`）

- **先验证再改，禁阿谀**：不说「你说得对／好建议／谢谢」，直接改并说明改了什么（Actions > words）；验证前不实现
- **不清楚全停**：有条目没看懂就停下来问，不要先改清楚的（条目可能相关，部分理解=错误实现）
- **YAGNI 检查**：意见要你「正经实现」时，先 grep 实际调用，没人用就删而不是加
- **该 push back 就 push back**：意见在本代码库不成立/破坏现有/与架构决定冲突——用技术理由反驳（引用工作测试或代码），架构级拉用户；外部或自动 review 工具的意见同样先怀疑、验证再定
- **自己 push back 错了**：事实陈述纠正，不长篇道歉

### 主线程纪律

主线程只调度不写实现代码（除纯文档/单行修）；用 TODO.md 或本地计划文件跟踪进度；子线程返回后**必须核验**实际改动。

### 子线程并行派发（run_in_background）

步骤 3 派发时，**无依赖关系的任务组用 Agent 工具的 `run_in_background` 后台派发**，多个独立组可同时派，主线程不得阻塞干等（2026-08-20 会话分析：纯「派发→阻塞干等→验收」串行模式累计 ~40h 纯等待，引以为戒）。存在并发 change 时，派发前跑一次 `bash scripts/harness/concurrency-status.sh`（见 §0.6「commit 与归档解耦」）——树上若有归属其他 active change 的文件，重命令（全量 lint/build）可考虑错峰，避免对同一棵混合树重复跑。

| 要点 | 做法 |
| ------ | ------ |
| 档位选择 | **实现/验证/通用任务用 `general-purpose` 档（覆盖档，兼实现档职能——原 implementer 档 2026-11-03 并入退役，能力完全拉平）；只读探索用 `explore`/`plan`（覆盖档：skills/插件已开、无写工具、不开 codemode，2026-10-13 上线）；审查用 `change-review`（只读通用档，不绑模型，模型派发时指定）；UI 原型编辑用 `ui-design` 档（项目自定义档：只改当前 change 的 `ui-prototype/**` 与 `ui-design.md` 的 Prototype 节，不绑模型——原型审美任务建议用强模型）**（explore/plan/general-purpose 均为 `.pi/agents/` 项目覆盖档，`load_extensions: true` + `load_skills: true`，general-purpose 另开 `codemode: on`，harness 约束注入与档位继承生效，矩阵见 [`harness/pi-extensions.md`](harness/pi-extensions.md)「子线程通道矩阵」）。**放行边界**：UI 合同未就绪（major 原型待批）时，`ui-design-gate` 阻断具备写能力的实现子线程派发与项目代码写入，但放行只读档与原型编辑档的派发（留痕 `ui-dispatch-allowed`）——原型档经 `edit`/`write` 工具的每次写入仍逐个过门禁，越出当前 change 目录（`front/` 等）照常阻断（shell 类通道不在本门禁覆盖范围——既有边界）。AGENTS.md 不注入子线程（pi-web 硬编码 `noContextFiles`），覆盖档 addendum 已写「开工先自读 AGENTS.md」兑底；派发任务文本 MUST 带相关域红线摘要 + 必读文件清单（前台派发尤其）；取数三步与 brief 模板见下节「步骤 3 派发前取域红线」 |
| 并行条件 | 任务组间无数据/产物依赖（如两个不同 domain 的实现、文档起草 vs 后端任务） |
| 等待期 | 主线程不闲着：做验收准备（预跑门禁命令）、起草文档、或串行做只能主线程干的活（调度 / review 计划） |
| 收口 | 全部用 `get_subagent_result` 统一逐个验收；验收失败的 `steer` 重定向或 kill 后重派 |
| 红线 | 存在数据/产物依赖的任务**必须串行**：design 未完成不得派实现任务；同文件/同模块改动**不得并行派两个 agent**（写冲突 + review 混淆） |

#### 步骤 3 派发前取域红线（三步 + brief 模板）

「派发任务文本 MUST 带相关域红线摘要 + 必读文件清单」里的「带」由本节三步定死：**判域 → 取红线 → 粘 brief**，脚本 `--brief` 输出**原样**粘贴，禁自创格式（自创格式 telemetry 记不到，`harness-retro` 的「派发带域比例」会系统性偏低）。

1. **判域**：按目标路径反查（`--paths`）；路径未定时才按任务词查 [`constraints-index.md`](constraints-index.md) 域表。
2. **取红线**：`bash scripts/harness/constraint-digest.sh --brief --paths <目标路径>`（或 `--brief --domains <域1,域2>`）——输出 5–10 行/域；**不得**让主线程读整篇 flow 文档后自行摘要。不带 `--brief` 时输出人读形态（额外带「命中来源/未命中说明」旁注段），**不可**直接粘进 brief。
3. **粘进 brief**：`--brief` 输出原样粘贴（下方模板即真实输出形态），源路径必写（子线程要能复核）。

brief 模板（**= `constraint-digest.sh --brief` 的真实输出形态，是 telemetry 解析契约，禁止自创**）：

```markdown
## 约束（红线，源 docs/reference/flow/daily-report.md, docs/reference/flow/scheduler.md）
### daily-report（源 docs/reference/flow/daily-report.md）
1. **同 board 同日重跑必须整份覆盖重建（幂等），不得产生重复报告，并发写也不炸唯一约束**
2. **当天 tag 归属话题必须按到 topic 质心的余弦距离分 L1/L2/L3 泳道**
…（共 41 条，见细节层）
细节层：read `docs/reference/flow/daily-report.md`「业务约束与不变量」
### scheduler（源 docs/reference/flow/scheduler.md）
1. **调度器清单必须由 scheduler.Registry 自动发现，不得在 handler 维护第二份 descriptor 列表**
…
细节层：read `docs/reference/flow/scheduler.md`「业务约束与不变量」
> 目标路径与本清单冲突时以 `--paths <你的目标>` 输出为准
```

模板最后一行是**子线程自取兜底**：brief 漏了域，子线程按自己真实目标路径补取（`bash scripts/harness/constraint-digest.sh --brief --paths <自己的目标>`），不靠主线程记性。域清单唯一真相源 = `docs/reference/flow/*.md` basename（脚本 `--domains` 只认它）。

> **与无档编辑路径 JIT 的分工**（enable-unbound-jit-injection）：未激活档会话/子线程在**写/编辑代码命中 `doc-impact-applies` 标签路径**时，constraint-injection 会自动把对应域约束节经动态层注入（路径标签是文件系统事实、零歧义）。本节三步**不变、仍必做**——brief 覆盖的是**自动注入覆盖不到的场景**：纯问答/规划/评审（无编辑动作）、路径未定时按任务词判域、以及跨域补充（一个任务跨多个域时显式列出）。机制见 [`harness/pi-extensions.md`](harness/pi-extensions.md)「无档编辑路径 JIT」。

### 供应商与模型选择（子线程派发参考）

> ⚠️ **硬规则：Agent 的 `model` 参数必须用 `provider/modelId` 全称**（如 `zai-coding-cn/glm-5.3`），**禁止用 fuzzy 名**（如 `glm-5.3`）；想用默认供应商时**省略 `model` 参数即可**（默认即 `zai-coding-cn/glm-5.3`，显式传 fuzzy 名反而绕过默认、落到错误供应商）。实时清单查 `pi --list-models`。
>
> 原因：pi 里有 10 个 model id 跨多个 provider 重复注册（`glm-5.3`/`glm-5.1`/`glm-4.7`/`glm-5-turbo`/`glm-4.5-air`/`glm-5v-turbo`/`deepseek-v4-pro`/`deepseek-v4-flash`/`mimo-v2.5`/`mimo-v2.5-pro`）。fuzzy 名会按字母序解析到**非预期**的供应商——实测传 `glm-5.3` 会落到 `opencode-go`（字母序最先），而不是默认供应商 `zai-coding-cn`。glm 系列统一走当前默认供应商 `zai-coding-cn`（国内 coding 专用），优于 `zai`（国际站）/ `opencode-go`（聚合网关）。

> 🚦 **额度门禁（quota-gate）操作纪律**：派发前 quota-gate 自动查额度（机制见 [`harness/pi-extensions.md`](harness/pi-extensions.md) §派发额度门禁），低额度时派发被硬 block。收到阻断 reason 后：按 reason 提示**换有额度的 provider 全称重试**，或等窗口重置——不要原地反复重派同一 provider。

## 1. 任务拆解规范

apply 启动时将 proposal 垂直切片为 tasks.md 可独立交付子任务；每个子任务含验收标准 + 关联 checkbox；配了 issue tracker 的同步建 issue。

## 2. 实现纪律 — 用例先行

> 用例设计前置到 specs 阶段，测试代码与实现的编写顺序解绑（可先可后可交织）；测试失败难定位加载技能 `systematic-debugging`（四阶段根因调查，未确认根因前不得乱改）。（规则演进：2026-08 前为严格 TDD red-green，amend-dev-workflow 改用例先行——agent 工作流下「先看到失败」的两轮往返 token 成本高且实现中途调整即返工；想清楚测什么的「设计前置」不放松，放松的只是「代码先跑红」仪式。）

**铁律：没有用例设计，不动手写实现。** 用例设计的家：spec.md 的 Scenario（WHEN/THEN）即黑盒行为用例。

> 用例设计标准（测试单元=一个 Requirement+其 Scenario、四问句：节拍/变体/层选择/效果核对、验收措辞黑名单）见 [`standard/shared/test-design.md`](standard/shared/test-design.md)——写 specs/tasks/测试代码时由 constraint-injection JIT 自动注入摘要。

| 场景 | 要求 |
| ---- | ---- |
| 新增模块 / 核心逻辑变更 | specs 阶段完成 Scenario 用例设计；复杂逻辑另出白盒用例文档（见下） |
| 复杂逻辑（状态机≥3状态循环 / 算法 / 多模块交互协议） | 派子线程枚举白盒用例（分支表/边界值清单）落 change 目录；**断言判据（什么算对）主线程定，子线程只做机械枚举** |
| Bug 修复 | **先写复现测试再修代码（不可豁免）**——先复现才能证明修的是这个 bug |
| 现有代码小幅修改 | 至少补充回归测试 |
| 纯配置 / SQL 迁移脚本 | 豁免（但需人工验证） |

**测试代码与实现顺序解绑**：同 change 落地即可，无需证明「测试先于实现」或「曾看到失败」；归档时 tasks.md 验证节列 Scenario→测试文件映射，未映射的 Scenario 视为未覆盖。

**复杂度声明制（proposal 头机器可读声明）**：新 change 的 proposal.md 头部 MUST 携带 `<!-- complexity: complex -->` 或 `<!-- complexity: simple -->`（与 `constraint-domains` 同款 HTML 注释惯例，独立成行置于头部）。判定：状态机≥3状态循环 / 算法逻辑 / 多模块交互协议任一命中 → complex，其余 simple——复杂度是设计阶段判断（propose 时点），不是实现事后归类。机器执行（不靠自觉）：声明 complex + 缺 test-cases*.md → entry-gate 在 implementation 档动工首回合 steer 提醒、spec-gate ⑤a 归档 warn 强违例；声明 simple / 未声明但任务行命中兜底关键词（算法/状态机/解析/协议）→ 反向质询（改声明或补文档）；词表不扩容（主信号=声明）。openspec 官方 skill（new-change/propose/continue）不植入本仓库定制项，声明义务以本节为准。

**红旗（遇到即停）**：动手前 specs 无 Scenario / proposal 缺复杂度声明 / 复杂档缺白盒用例文档 / bug 修复无复现测试 / 归档验证节无 Scenario→测试映射——停下补齐再继续。

## 3. 复杂设计验证（先脑暴 → 后原型）

设计边界不清 / 需求多解 / 交互形态未定时，先加载技能 `brainstorming` 做纯对话探索（澄清意图、列方案、定取舍，**不出代码**），收敛后再进实现。

涉及状态机（≥3 状态循环流转）/算法逻辑/多模块交互协议（API 契约/事件总线）**必须先做可丢弃原型**：输出方案对比+选型理由+风险点入 `openspec/changes/<name>/`，确认后销毁再进实现（原型阶段的白盒用例枚举可与此并行，见 §2）。

> brainstorming 是「先聊清楚」（轻、纯对话），原型是「用代码验证」（重、出代码）——不要跳过 brainstorming 直接堆原型。

### 3.1 UI 原型通道（与复杂逻辑原型正交）

UI 影响由 proposal 的 `<!-- ui-impact: none|minor|major -->` 独立声明，与 `complexity` **两维度正交**——治理面板可以逻辑简单但 UI major，解析器重写可以逻辑复杂但 UI none。两条原型通道各走各的，互不替代：

| 通道 | 触发 | 制品 | 确认方式 |
| ---- | ---- | ---- | ---- |
| 复杂逻辑原型 | `complexity: complex`（状态机/算法/协议） | 方案对比+选型理由入 change 目录，确认后销毁 | 用户对话确认，无机器 marker |
| UI 原型 | `ui-impact: major`（新页面/面板/弹窗/导航/多步/信息架构/布局模式） | `ui-design.md` 八节合同 + 三节结构化声明（`## Interaction Decisions` / `## Data Provenance` / `## 明确不做`）+ 按主模式分流的可丢弃原型（canvas 用 `states/` 三态图 + `interaction-table.md`，其余用可点 HTML）+ `<!-- ui-approval: pending|approved -->` | **用户对话明确确认后才可改 approved**；信息架构/主流程/布局模式修订后 MUST 重置 pending |

UI major 且 approval=pending 时：propose/continue 停在 requirements 档展示原型，apply 前置检查与 `ui-design-gate` 扩展（implementation 档）双重拦截实现派发与项目代码写入（当前 change 的 ui-design.md / ui-prototype/** 修复不受限）。布局选型（reader=760 / contained=1120 / workspace / split、dialog sm/md/lg/xl）权威见 [`standard/frontend/layout.md`](standard/frontend/layout.md)；**交互模式怎么选、界面文字放什么、原型受什么预算约束**见 [`standard/frontend/interaction.md`](standard/frontend/interaction.md)。

#### 3.1.1 契约先行：L0–L3 四层阶梯

UI 设计 MUST 按四层推进，每层只对自己那一层的判断负责：

| 层 | 谁做 | 产出 | 硬约束 |
| ---- | ---- | ---- | ---- |
| **L0 契约** | 用户 + 强模型，**1 轮** | `ui-design.md` 的 `## Interaction Decisions` / `## Data Provenance` / `## 明确不做` + 区域骨架 | **唯一需要用户批准的东西**；这三节不定稿不往下走 |
| L1 骨架 | 便宜模型 | 空壳截图（区块只有标题） | 只能出现 L0 的区域；**禁止任何业务文案** |
| L2 交互 | 强模型 | 空态可点原型，或画布类的「状态图 + 操作表」 | 不得新增 L0 之外的控件；模式必须与 L0 台账一致 |
| L3 数据 | 便宜模型 | `fixture.json` → 原型 import | 字段 ⊆ provenance 表；禁止手写/内联数据 |

> **阶段可机器识别**：`ui-design.md` 头部可写 `<!-- ui-stage: l0|skeleton|interaction|data|approved -->`。当前**只记账不阻断**（`add-ui-stage-accounting`）：触发条件按写入路径不按档位，`l0` 禁写 `ui-prototype/`、`skeleton` 只许写 `ui-prototype/skeleton/`，越域记 `ui-stage-scope-out` warn。观察期数据达标后才转阻断。

**铁律：L1–L3 不允许新增 L0 之外的任何元素。** 越出契约即停下回问用户，不得自行“顺手丰富”——实测反例：某 change 为求全面，在原型里内联整份数据集（单文件 11MB、`fake` 值 163 处），实现阶段才发现后端无数据源。

#### 3.1.2 评审阶梯：每轮只裁一个决策

人的注意力是稀缺资源（实测经验：超过 3 轮反馈就聊不动）。因此评审 MUST 分轮且每轮只给一个决策：

| 轮 | 给什么 | 用户只裁什么 |
| ---- | ---- | ---- |
| R0 | 3 个交互模式选项（附判据编号 P1–P5）+ 区域骨架 | 选哪个模式 |
| R1 | 骨架截图 | 区域划得对不对、层级对不对 |
| R2 | 空态可点原型 / 状态图 | 这条操作路径顺不顺 |
| R3 | `fixture.json` 摘要（≤1 屏） | 这些数是不是我会看到的东西 |

**R0–R2 禁止业务文案。** 没文字可堆时，agent 只能用结构说话——这一条几乎单独消灭“往原型堆说明”问题。每轮的产出 MUST 是可以被看一眼的东西（截图 / 状态图 / 一屏 JSON），SHALL NOT 是一段文字汇报。

#### 3.1.3 分批纪律：按契约切批，不按模块切批

多模块 UI（如九个节点）拆开做是合理的，但**切分维度 MUST 是契约层（L0/L1/L2/L3），SHALL NOT 是业务模块**。

反例：`add-home-pipeline-status-page` 按模块串行派发 22 次 `ui-design` 子线程（FB-2 用户指令「各自把每个模块都做一遍，然后统一让我看看」），结果每个子线程都拿到一个模块边界、必须独立回答“什么交互、什么数据、怎么说明”，产出 61 份 md（10,360 行）+ 33 份 html（65,600 行）+ 402 张版本截图，合计 174MB，且直到最后才被审阅一次。不是分批错了，是**分批时没有契约、且把审阅推到了最后**。

正确做法：L0 由用户 + 主线程一次定稿；L1–L3 可以多个子线程并行，但每个子线程的 brief MUST 包含 L0 的三节原文，且产出 MUST 收敛回**同一份**决策表 + **1 个**入口原型 + **1 个** `fixture.json`，SHALL NOT 每模块各产出一份设计说明书。

**门禁分层**：约束注入（[`.pi/extensions/constraint-injection.ts`](../../../.pi/extensions/constraint-injection.ts) 在 `before_agent_start` 每 turn 自动注入：flow「业务约束与不变量」节按关键词命中、standard 文档按编辑路径 JIT 命中——注入管"知道"）→ 增量（pi extension 每回合 `turn_end`，**会话内增量路由**：仅本回合相对快照新增/变化的路径命中对应侧才跑——后端命中跑 `golangci-lint`+`go vet`+`go build` 并经 [`scripts/harness/change-scope.sh`](../../../scripts/harness/change-scope.sh) 路径映射自动跑影响包 `go test -short ./internal/<domain>/...`（`-short` 下 DB 集成测试自动 skip，无需 Docker），前端命中才跑 `pnpm lint`；会话前残留脏文件不触发，上回合失败未转绿粘性重跑；[`.pi/extensions/quality-gate.ts`](../../../.pi/extensions/quality-gate.ts)，harness-observability-fixes 引入）→ 日常验证（agent 手动跑完整影响包测试 `bash scripts/harness/change-scope.sh` 看命令清单 / `pnpm test:unit`）→ 归档全量（§11：`go test ./...`+`go build ./...` / `pnpm build`+`nuxi typecheck`）。增量不跑前端 typecheck/build/test（**门禁分层设计**：这几类留给 agent 手动执行与 §11 归档门禁兜底，与执行平台能力无关）+ 完整门禁由 §11 兜底；门禁命令的执行链路按宿主平台分流（`cmd.exe` 可达则 windows 模式经 interop，否则 native 模式走本机工具链，见 `openspec/specs/gate-interop-health/spec.md`）。真 Claude Code/Codex 无 pi extension，需手动跑增量门禁（红绿态可查：`bash scripts/harness/gate-status.sh`，只读）。

**全量兜底通道——滚动分片巡检（test-debt-patrol）**：增量门禁只覆盖被碰 domain（platform/骨架档不测）与前端 lint，跨 change 的存量红无自动兜底——由 [`scripts/harness/test-patrol.sh`](../../../scripts/harness/test-patrol.sh) 接盘：把全量测试拆成静态分片（后端 6 片 + 前端 6 片，前端硬约束 `--maxWorkers=2`），按「最久未巡优先」一次推一片，N 天滚完一轮；巡检结果写 `patrol.check` 事件，失败测试进 `test_debt` 台账（`.pi/harness/events.db`）。撞见非本 change 红测试按 §11.4 记账后放行。用法与分片清单见 [`standard/backend/testing.md`](standard/backend/testing.md) / [`standard/frontend/testing.md`](standard/frontend/testing.md)「巡检分片」，机制见 [`harness/pi-extensions.md`](harness/pi-extensions.md)。

**影响包机械判定（change-scope）**：[`scripts/harness/change-scope.sh`](../../../scripts/harness/change-scope.sh)（add-change-scope 引入，思路源自 deepseek-harness）按 git diff 改动路径 + 目录自动发现的三档映射输出最小验证命令（domain 档 `go test -short ./internal/<domain>/...` / platform 档全量 vet / 骨架档 build+vet / 前端 lint；未命中路径报「无法判定」绝不猜测）。`--json` 供 quality-gate 消费。新增 domain 目录零维护（运行时发现）。「测试只跑影响包」以此脚本为准，不再靠自觉。

**派发额度门禁**：除质量门禁外，[`.pi/extensions/quota-gate.ts`](../../../.pi/extensions/quota-gate.ts) 在 `tool_call` 拦截 `Agent` 工具调用做供应商额度预检（GLM/Kimi 查 5h/周窗口百分比、DeepSeek 查余额，opencode-go 无 API 放行），额度不足 block 并把中文 reason 喂回主线程换模型重试；查询失败 fail-open 不阻断（fail-open 放行落 custom_message 留痕，2026-08-20 起）。阈值/缓存 TTL 走环境变量（`QUOTA_GATE_WINDOW_PCT`/`QUOTA_GATE_MIN_BALANCE`/`QUOTA_GATE_TTL_MS`），设计见 openspec change `agent-quota-gate`。

**归档就绪自查（archive-readiness，harden-archive-readiness 引入）**：[`scripts/harness/archive-readiness.sh <change>`](../../../scripts/harness/archive-readiness.sh) 与 spec-gate 同口径五项检查的聚合只读自查（①②③④⑤同一批脚本，单一事实源；⑤ review-trace 为 add-review-trace-gate 新增）；**归档前先跑它，全绿（退出码 0）再 `openspec archive`**——一次看清全部缺口再补，勿被门禁拦一次补一项试一次（2026-09-19 体检：单 change 归档 7 连试，`m7.block_recur_groups=5`）。UI 验收证据项不在自查范围（仅门禁校验）。

**归档硬门禁（spec-gate）**：[`.pi/extensions/spec-gate.ts`](../../../.pi/extensions/spec-gate.ts) 在 `tool_call` 拦截 bash 里的 `openspec archive` 命令，放行前强制五项检查 + ⑥' UI 验收：① `doc-impact.sh verify <change-dir>` 退出码 0（反向启发式双轨输入：事实库存在该 change 的 `edit.map` 归属集合且非空时只扫归属集合，其他 active change 的脏文件不再干扰；无记录/空/库不可用回退全树 git diff 且命中仅提示不判 FAIL；两轨统一剔除工具自管文件与共享文档黑名单——fix-doc-impact-misattribution，跨 change 误报源消失后 `doc-impact-excuse` 退役，既有注释读取兼容）；② `check-standards.sh --change <change>` 无失败（A-E/G-H 仍全仓检查，**F 段只对账归档目标**）；③ `check-tasks-tail.sh <change-dir>` 退出码 0（tasks.md 尾三节测试/文档/验证各自独立匹配 + `<!-- doc-impact:` 声明标记 + complex 档 review 任务行判定（review-task-frontload：proposal 头部声明 `<!-- complexity: complex -->` 且未 `<!-- review: waived -->` 豁免时，tasks 须含 review 任务行，缺则红出两条修复指引；simple/无声明 change 不受影响）；判定已抽出为独立脚本，与 archive-readiness 自查共用同一事实源，harden-archive-readiness）；④ `scenario-trace.sh <change-dir>` 退出码 0（Scenario→测试映射对账，scenario-test-mapping-gate 引入，格式见 `openspec/specs/scenario-trace-gate`）；⑤ `review-trace.sh <change-dir>` 退出码 0（review 痕迹对账，add-review-trace-gate 引入：review.md 建账（条目格式见「review 执行要点」第 4 点）或 proposal 头部 `<!-- review: waived -->` 显式豁免，两者皆无/空壳文件均阻断；存量 in-flight change 不豁免，归档前补一行业无发现声明即可，格式见 `openspec/specs/review-trace-gate`）。任一失败 block + 中文 reason（含修复指引与 archive-readiness 自查指引）；豁免通道 `--force` / `SPEC_GATE_BYPASS=1`（记 warning 留痕不静默）；开关 `SPEC_GATE_ENABLE`（默认开）/`SPEC_GATE_TIMEOUT_MS`（默认 60s）。①②④⑤均不跑测试（§11.1 条件 1 仍归 agent 手动）。另：**检查⑤'（warn 级不 block，coordinate-concurrent-changes）**：`concurrency-status.sh --check <change>` exit 2（树上存在归属其他 active change 的未 commit 文件）→ steer 提醒拆 commit/协调收口 + `policy.decision(warn, concurrent-dirty-tree)` 记账；exit 3（冷启动全无归属/库不可用）零输出。**⑤/⑤' warn 投递为边沿触发（edge-trigger-archive-gate-warns）**：同会话同指纹（warn 内容未变）至多一条，指纹变化 / 新会话 / session_compact 后重发，上次 warn 过本次转净（exit 0 / 零违例）发一行「已转净/已清零」收尾；warn 记账与展示同边沿；bypass / fail-open / 无名 fail-open 的 warning 不去重（审计留痕）。机制详见 [`harness/pi-extensions.md`](harness/pi-extensions.md)「归档门禁 warn 边沿触发」节。

**全量测试软守卫（test-scope-guard）**：[`.pi/extensions/test-scope-guard.ts`](../../../.pi/extensions/test-scope-guard.ts) 仅在识别出**真·全量后端测试**时介入（harden-test-scope-guard 收窄：裸 `./...`/`...` 包模式 + 生效 cwd 解析为仓库根 `backend-go`；引号内文本、`#` 注释、heredoc 正文、`cat` 重定向目标掩蔽后不参与判定；`bash -c` 内联脚本递归；影响包/子树/单包命令一律放行）。扫描通道覆盖 bash、`ctx_execute`（仅 `language=shell`）与 `ctx_batch_execute`。放行语境：命令或近期上下文含 归档/§11/archive/验证节/pre-push 或 /依赖变更|建议全量/（change-scope.sh 官方建议语），或命令带 `# archive-gate` / `# allow-full-test` 逃生注释，放行时附 test-patrol 登记指引；`TEST_SCOPE_GUARD=soft|hard|off` 默认 soft（hard 才 block）。

**门禁裁决记账（policy.decision）**：spec-gate / quota-gate / test-scope-guard 的显著裁决（`block` / `warn` / `bypass` / `fail-open` 四种 action）统一追加 `policy.decision` 事件到事实库（保留 30 天，harden-harness-policy-and-spill 引入），普通成功放行零记录、quality-gate/entry-gate 继续只用 `gate.check` 不双写；记账经共享 helper `.pi/extensions/lib/policy-decision.ts` 收敛 payload（reasonCode 稳定 kebab-case 枚举、target 仅 change/provider 短摘要，禁合命令/密钥/响应正文），写入失败严格旁路不影响裁决。定期健康复盘查法见 skill `harness-facts` 查询配方 §7/§8。

| 验证目的 | 工具 / 执行者 | 理由 |
| -------- | ------------ | ---- |
| **交互流程验证**（多步导航、点击、tab/面板激活、数据渲染对不对） | **agent-browser**（主线或子代理 bash 调 agent-browser CLI） | 无头驱动真实浏览器走真实前端产物；导航/点击/视口切换/网络拦截均可脚本化，snapshot 可程序化断言 |
| **视图/视觉验证**（截图看布局/样式/响应式对不对） | 派 **zai-coding-cn/glm-5.3-flash** 子代理截图判断 | 主观视觉/审美判断，视觉模型优于通用模型（用户约定 2026-09，替代 kimi-coding/k3） |
| **页面骨架/响应式 smoke**（CI 可重复、需纯净隔离） | Playwright `tests/e2e/*.spec.ts`（仅极稳定 smoke） | 独立实例无浏览器依赖，适合 CI；业务交互回归脆弱**不堆** |

**agent-browser 前置**：Web 验收一律走静态托管 `http://localhost:5100`（`bash scripts/dev/deploy-frontend.sh` 铺盘后的产物，勿对 dev server 做验收）；无头模式不抢用户当前窗口。

**铁律**：`click` 触发 Vue 状态变更后，DOM 在 nextTick 才重渲染——**必须等一拍（`agent-browser wait` 或重取 snapshot）后再做状态断言**，同步读得旧值=假阴性（头号坑）。

**派发要点**：agent-browser 交互验证给子代理「导航路径 + 断言脚本」，断言写成代码（读 snapshot 原始值，python/grep 机械判定），**不让模型主观判断对错**；导航路径见 [`architecture/ui-navigation.md`](architecture/ui-navigation.md)，命令用法见 skill `agent-browser`（`.agents/skills/agent-browser/`）。

**major UI 双层验收（对照已批准基线，make-ui-design-first-class + add-ui-verification-trace-gate）**：声明 `ui-impact: major` 的 change 完成验收 = ① agent-browser 主交互链路机械断言 + ② **1440×900 与 1920×1080 两档视口**的视觉检查（布局符合 ui-design.md 所选 layout mode、无横向溢出；窄屏支持另加）+ ③ 实现与已批准基线的差异说明（可点 HTML 原型类：逐交互对账；**canvas 类：三张状态图逐态对账 + `interaction-table.md` 六列逐行对账**，不需要可交互页面）。上述证据 MUST 以 `ui-verification/report.md` 建账（`### A-<N> <场景>【pass|fail|未覆盖】` + 依据行；未覆盖写原因），条目点名的截图 MUST 落 `ui-verification/` 目录（**仅本地留存、不入 git**——2026-10-30 起 `.gitignore` 已挡 openspec 下图片与 `changes/**/ui-prototype/`，勿 `add -f` 硬加；门禁对账的是本地文件存在性）。只有组件单测不算完成 major UI 验收；「字样齐备无实物」（tasks 写了 agent-browser/双视口字样但无建账与截图）同样不算——归档门禁检查⑥' 由 `scripts/harness/ui-verification-trace.sh` 单一事实源机器拦截，spec-gate 记 `ui-design-gate` block `ui-verification-missing`。minor 验收映射须指名道姓：组件测试写出真实存在的测试文件路径，agent-browser/人工验证在 report.md 有 ≥1 条判定条目。验收分流细则见 [`standard/frontend/layout.md`](standard/frontend/layout.md)。

**前端验收四维度（split-board-upgrade-directions 补修确立，2026-09-07）**：前端验收按维度对账，缺维度=验收不完整。上面的工具分流表回答「用什么工具」，本表回答「验哪个维度、验到什么程度」：

| 维度 | 验什么 | 最低要求 | 手段 |
| ---- | ---- | ---- | ---- |

| **迁移完整性** | 旧入口/旧能力是否仍有可达路径，而不是只在新页面/新 spec 里写「已迁移」 | 任何路由/宿主/壳/tab 替换：旧→新去向表 + ≥3 条真人主故事；遗漏记 High | review.md 去向表 + agent-browser 实际路径 + 旧动作调用点 grep |
| 证据存在性 | 勾选的任务有实物对得上 | 声明「截图留证」的任务，截图 MUST 落 `openspec/changes/<name>/ui-verification/`；tasks 勾了 [x] 但目录无对应文件 = 空转 | 机器对账：`scripts/harness/ui-verification-trace.sh`（建账条目 + 点名截图存在性，add-ui-verification-trace-gate） |

教训锚点（2026-10-25，rework-workshop-into-radar-and-desk 用户投诉）：新工坊验收账本已有 40+ 条 pass，仍漏「无活跃泳道但有日报时读不到」「归档点开只有外链、没有站内正文」「历史格子看归档回最新日」「删除版块无新入口」——这些不是截图缺失，而是**验收只证明新页面存在、没证明旧故事可完成**。补丁：上方「迁移完整性」维度 + review 1.5 去向表 + [`standard/frontend/layout.md`](standard/frontend/layout.md)「UI 复审的全系统与产品任务覆盖」；后续 review 不得再用「面板能打开」充当主故事通过。

## 7. 架构体检

### 7.1 codegraph 代码图检查（强制）

每个子任务完成后必须执行：

1. `codegraph impact <修改的符号>` → 影响分析，确认波及面无 HIGH/CRITICAL 风险被忽略
2. `codegraph affected <改动的源文件>` → 变更检测，确认受影响测试文件范围符合预期

- `impact` 返回 HIGH/CRITICAL 风险必须暂停向用户报告，不得忽略
- **已知局限 1**：codegraph 无法追踪 Gin handler 的 `group.GET/POST(..., fn)` 注册模式，会把仅由路由注册引用的 handler 误报为「无调用者」（约 26 个误报）。删除 Gin handler 前必须用 `grep` 二次校验其是否被路由注册引用，避免误删
- **已知局限 2·顺传导链深查**：`codegraph impact` 只显示**直接调用面**，看不到跨层/跨域的**隐式传导**（如「改截断排序 → 经 LLM 聚类输入 → 打散 topic 锚定」）。若改动处于某条传导链上（查 [`coupling-map.md`](architecture/coupling-map.md)），必须人工顺链推导下游影响，不能只看到直接 impact 就收工。踩到/分析出新的跨功能传导耦合，**必须往 `coupling-map.md` 补一条**（含守卫测试）

### 7.2 架构合理性检查

退一步做全局审视（zoom-out，不再挂技能）：新增模块与现有系统耦合度、是否引入循环依赖、是否符合现有分层（后端 `internal/{reader,tagmanagement,topicgraph,admin}` + `internal/platform/*`；前端 Vue 3 Composition API + Pinia）。耦合过高则暂停并提出重构建议。

## 8. 变更控制

> apply 阶段允许按需调整 proposal/spec/design/tasks 范围，但调整须**留痕可溯**。

| 程度 | 判据 | 处理 | 与 plan mode 关系 |
| ---- | ---- | ---- | ----------------- |
| 局部澄清/纠错 | 单个 task 实现细节调整、字段名修正、补充边界条件 | 就地改 spec/design/tasks + tasks.md 留痕 | 不需重新 ExitPlanMode |
| 范围扩展 | 新增 1-2 个 task、补遗漏的需求场景 | 就地改 + tasks.md 留痕 + 通知用户 | 不需重新批准，但回复中告知范围扩大 |
| 中等重构 | 重写 >3 个 task、换核心数据结构、改 API 契约形状 | 就地改 + tasks.md 留痕 + **重新 ExitPlanMode 获用户批准** | 需重新批准（plan 核心假设变了） |
| 方向性变更 | 换技术栈、改核心目标、推翻 proposal 根本目标 | **新开 change** 或 archive 旧的 | 新 change 走完整 propose→apply |

> 用户对范围变化有知情权：哪怕就地改，只要扩展了批准范围（新增 task、改了对外契约），必须在回复里明说。

- 禁止在代码注释写「TODO：后续优化」却不记录到 tasks.md
- 归档前禁止跳过 §11 归档门禁；验证节命令未实测通过的 change 不得 archive

## 10. 数据兼容性检查

涉及后端数据层变更时，必须在 tasks.md 增加兼容性验证子任务：

- **PostgreSQL DDL 变更**（GORM AutoMigrate/显式迁移）→ 必须用 testcontainer PG + 历史数据验证迁移（先插历史行再跑迁移，验证回填/NOT NULL/数据完整/索引），或本地起 PG 跑一次迁移看启动 SQL 日志；SQLite 空库迁移**不算**覆盖。model tag 规范见 [`code-style.md`](standard/backend/code-style.md)「GORM model tag 与迁移」，迁移/JSONB 陷阱见 [`testing.md`](standard/backend/testing.md)

- **GORM 模型字段变更** → 确认 JSON API 响应格式不受破坏性影响
- **配置文件**（`config.yaml`）新增或修改字段 → 同步更新 `docs/reference/configuration.md`

## 11. 归档门禁（Archive Gate）

> 提交前门禁（§4.1/§5.1）覆盖代码质量；归档门禁覆盖「代码↔文档一致性 + 验证可复现」。

### 11.1 归档前置六条件（缺一不可）

> **声称完成前的铁律**（加载技能 `verification-before-completion`）：必须实际跑验证命令并**亲眼确认输出**——不得「看没报错就说过」「命令没跑就说跑过」「上次过了这次肯定过」。归档门禁就是这道理的最后一道关。

1. **测试通过**：§4.1（后端）/ §5.1（前端）/ §6（集成）门禁命令实测通过；纯文档 change 豁免代码测试，但必须在「验证」节附 grep 一致性校验（幽灵路径/调度器/命令、版本号、旧包名零残留）
2. **文档同步**：§9 产出物清单全部勾选，`docs/reference/` 已反映新代码状态
3. **验证可复现**：tasks.md「验证」节（见 §11.2）每条命令实测零失败
4. **Scenario 映射对账**：`bash scripts/harness/scenario-trace.sh openspec/changes/<name>` 退出码 0——delta specs 中每个 ADDED/MODIFIED/RENAMED 的 Scenario 在「验证」节映射表（`| Scenario | 测试文件 |`）有对应行且映射的测试文件真实存在；无自动化测试的 Scenario 显式映射为「人工…」留痕；无 delta Scenario 的 change 直接通过（spec-gate 检查④机器强制，格式约定见 `openspec/specs/scenario-trace-gate`）
5. **review 痕迹对账**：`bash scripts/harness/review-trace.sh openspec/changes/<name>` 退出码 0——review 做了在 change 目录留 `review.md` 建账（`### R-<N> <日期>【High|Medium|Low】<标题>` + 状态行，零发现写 `- 审毕无发现（审查范围：…）` 声明行），不做在 proposal.md 头部声明 `<!-- review: waived -->` 显式豁免；两者皆无/空壳文件均阻断（spec-gate 检查⑤机器强制，add-review-trace-gate；单文件小修不豁免；waived 占比进 retro 统计防滥用；格式见 `openspec/specs/review-trace-gate`）
6. **UI 验收证据（新 schema change，spec-gate 检查⑥'）**：判定单一事实源为 `bash scripts/harness/ui-verification-trace.sh <changeDir>`（add-ui-verification-trace-gate）——major 须 `ui-verification/report.md` 建账（`### A-<N> <场景>【pass|fail|未覆盖】` + 依据行，未覆盖写原因）且条目/清单点名截图真实存在，规划制品（`ui-approval: approved` + 原型存在）由门禁另行校验；minor 须验收映射指名道姓（组件测试路径真实存在，或 report.md ≥1 条判定条目）；none 须 N/A 一致性；旧 spec-driven change 零检查不硬阻断。任一缺项阻断归档（记 `policy=ui-design-gate` block `ui-verification-missing`）；脚本缺席/spawn 失败按 fail-open warn 不阻断；`--force`/`SPEC_GATE_BYPASS=1` 豁免仍留痕（格式约定见 `openspec/specs/ui-verification-trace-gate`）

### 11.2 tasks.md 验证节强制结构

每个 change 的 tasks.md **必须**以三个固定尾节收尾：

- `## N. 测试` — 本次 change 影响的测试命令（后端 `go test ./internal/<pkg>`、前端 `pnpm test:unit`）
- `## N+1. 文档` — 需同步更新的 `docs/reference/` 文件。**格式**：第一行机器可读注释 `<!-- doc-impact: 域列表 -->`（apply 第 2 步写入，域列表见 `doc-impact.sh menu` 的 8 选项），下方人读 checkbox 列文件。无文档影响写 `<!-- doc-impact: none(理由) -->`。功能性 change 若触及 `flow/`，须声明将在 §12.2 补「变更溯源」链接（archive 后补）

  > **doc-impact-excuse 豁免**：verify 的「疑似遗漏」启发式（改了某域代码→该声明该域）可能误报——典型：改动语义不属该域（如改 `connect_postgres` 挂 trace 非 schema，不该动 `database.md`）、或工作树有其他 active change 脏文件干扰。确认误报后，在 `<!-- doc-impact: ... -->` 下一行加 `<!-- doc-impact-excuse: domain=理由; ... -->` 豁免。**只豁免「疑似遗漏」，不豁免「声明了未更新」（真没改文档）或「声明的文档不存在」**。

- `## N+2. 验证` — 每条**必须**是「可执行命令 + 期望结果」，禁止只写「已检查」（例：`go test ./internal/admin/scheduler → PASS`）；有 delta Scenario 的 change 须含 `| Scenario | 测试文件 |` 映射表（scenario-trace.sh 归档对账用，格式见 `openspec/specs/scenario-trace-gate`）

### 11.4 归档前自检

执行 `openspec archive` 前：

- 重跑 tasks.md「验证」节全部命令，确认零失败（若归档 skill 仅数复选框，归档前由人/AI 手动补这一步）
- **域外红登记台账**（test-debt-patrol 强制）：验证节/巡检撞见的失败测试若**不属于本 change 影响包**，用 `bash scripts/harness/test-patrol.sh --register <test_id> --context <change名>` 登记台账（或在 `--report` 里确认已在账），并在验证节写一句「域外红已记账」后方可归档——禁止「不是本 change 改坏的」不记录不处理。**本 change 影响包内的红不走记账通道**，必须修复后归档（§11.1 条件1 不变）
- 跑 `bash scripts/harness/doc-impact.sh verify <change-dir>` 对账（域注释 + checkbox 文件两层校验）。启发式误归因收敛（fix-doc-impact-misattribution）：①输入黑名单——工具自管文件（`openspec/changes/**/.openspec.yaml`、`openspec/changes/archive/**`）与仓库级共享文档（`AGENTS.md`、`constraints-index.md` 等）不触发“疑似遗漏”；②回退轨降级——`edit.map` 无归属记录时全树命中仅 stderr 提示（`[提示] 无法归属: <域>（全树回退仅提示）`）不判 FAIL；归属轨命中（会话真实编辑）仍 FAIL
- 跑 `bash scripts/harness/check-standards.sh --change <name>`：A-D 段（代码规范结构/domain 白名单/双主题/防孤立引用）+ **F 段（仅对账目标 change 的 doc-impact verify）** + **G 段（导航层文档死链检查）** 归档前必须零失败；E 段（flow 变更溯源链接）针对 archive 区，归档后校验（见 §12.3）。不带参数的 `bash scripts/harness/check-standards.sh` 保持人工全仓巡检语义，F 段遍历全部 active change。

## 12. 文档流转（Archive 即家 → Flow 反向溯源）

> §11 管 archive **前**门禁；§12 管 archive **后**活文档更新。archive 区是「永久归档家」，靠 `reference/flow/` 反向链接串联。

### 12.1 两段式流转

| 阶段 | 位置 | 责任节点 | 状态 |
| ------ | ------ | ---------- | ------ |
| ① 开发中 | `openspec/changes/<change>/` | propose → apply | 临时，可反复修改 |
| ② 归档（永久家） | `openspec/changes/archive/<date>-<change>/` | `openspec sync` + `openspec archive` | 永久归档，不再搬走 |
| ③ Flow 反向溯源 | `docs/reference/flow/<功能>.md` | archive 后由 change 作者补「变更溯源」行 | 活文档，链接回 archive |

`docs/v1.x/` 里程碑目录**降级为可选**：平时 archive 即终点；发版/做主题合集时才批量收进 `docs/v1.x/changes/`。

### 12.2 变更溯源链接（archive 后强制）

`openspec archive` 完成后，change 作者**必须**在受影响的 `flow/<功能>.md` 尾部「变更溯源」表追加一行链接回 archive 目录，格式如下（「归档位置」列**必须**含 archive 目录全名 `<date>-<change>`，供 `check-standards.sh` E 段校验）：

```markdown
| 日期 | 变更 | 摘要 | 归档位置 |
| 2026-06-14 | scheduler-cron | 定时任务改 cron 驱动 | archive/2026-06-14-scheduler-cron（归档缺失，示例占位） |
```

约定：一个 change 动多个 flow，每个受影响 flow 都补一行；纯文档 change / 不触及任何 flow：豁免（tasks.md「文档」节注明「无 flow 影响」）；链接用相对路径（flow 到 archive：`../../../openspec/changes/archive/<date>-<change>`）。

### 12.3 archive 后校验

补完变更溯源链接后，再跑 `bash scripts/harness/check-standards.sh`，E 段（flow 变更溯源链接）必须零失败。校验范围：新流程生效日（`2026-06-29`）之后的 archive change 必须被某 flow 文档引用；历史存量免校验。**溯源宽限期**（fix-doc-impact-misattribution）：归档未满 `GRACE_DAYS`（默认 3 天，`check-standards.sh` 顶部常量）的 change 免检——§12 本就是“归档后补溯源”流程，宽限窗内的债不 block 其他 change 的归档；超期未溯源仍 FAIL（债由本段催收）。tasks.md 声明「无 flow 影响」的豁免语义不变（宽限期不参与判断）。

### 12.4 流转完整性自检

archive change 已补溯源链接 + `check-standards.sh` A-G 段零失败 + `docs/reference/` 反映新代码状态。

### 12.5 归档后可选：跑一次 retro 回检

**可选人工步骤，不是门禁**（MUST NOT 接 hook、MUST NOT 进注入通道——报告是时变内容，进 system prompt 会破坏前缀缓存）：

```bash
bash scripts/harness/harness-retro.sh --days 7                 # 看本次改动有没有留下新噪声
bash scripts/harness/harness-retro.sh --save-baseline          # 或：改动 harness 规则前落基线
bash scripts/harness/harness-retro.sh --baseline               # 改完与基线对比同类指标
```

判定口径：同类指标（如某命令失败数、某 `policy+reasonCode` 的 warn 计数、注入面零命中文档数）**没降 = 改动无效或问题不在那**。改进项产出判据（每条必须绑定可回检指标 + 观察窗口；单 session 偶发不升格为规则；反 overfit）与七段解读（含⑦效能看板：插件 ROI/效率基线/返工信号）见 skill `harness-retro`；报告**不做判定、不自动开 change**，改进项仍走本规范 §0.6 编排。

何时值得跑：change 归档后、定期体检、怀疑某条软提醒/规则无效时、要改门禁阈值或注入规则前后（准 A/B）。窗口 > 30 天时与基线比会因 TTL 清扫而失真（报告头部会提示）。
