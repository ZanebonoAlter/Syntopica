# 测试用例设计标准（test-design）——故事锚点

<!--
doc-impact-applies: openspec/changes/, _test.go, .spec.ts, .test.ts | section=JIT 注入摘要
-->

> **权威源**：本文件是「测什么 / 测到什么程度 / 验收怎么写」的唯一权威源，跨前后端。
> 分工：「怎么跑」（框架 / 运行 / testcontainer / DSN 红线）见 [`standard/backend/testing.md`](backend/testing.md) 与 [`standard/frontend/testing.md`](frontend/testing.md)；「Scenario 即用例 + 复杂档白盒义务」见 openspec `case-first-testing`，本文件引用不重复。

## 单元模型：一个能力一个故事，用例文档串起来

**测试单元 = 用户故事 = spec 的一个 Requirement（能力切片）；完整故事由 change 目录下的测试用例文档（`test-cases.md`）串起来——spec 的 Scenario 是断言片段，不会把故事讲完整。**

- **用例文档是交付账本**：涉及行为的 change SHALL 产出 `test-cases.md`（纯文档 / 工具链 change 豁免），内容 = 把该 Requirement 的 Scenario 节拍串成主链路 + 变体走查 + 层选择落点 + 预期结果（模板见下节）。
- **双轨原则**：方法级单测（如纯函数解析器）允许且鼓励——毫秒级快反馈；但交付验收锚在用例文档的故事落点，方法绿 ≠ 故事绿。
- 为什么不锚方法也不锚片段：单盯一个方法的上下限跑通，回答不了「用户会发生什么」；单看 Scenario 片段，看不到跨节拍的完整旅程（空串表达式对方法是返回空数组，对故事是「用户提交后界面说什么、建了永不命中的关注还是被拦」——那是产品决策，只有串起来才暴露）。
- 设计动作：写 specs 时按故事想节拍；写 test-cases.md 时串主链路+变体+层；写 tasks 时验收引用用例条目；写测试代码时先落故事层，再补方法级快反馈。

## 测试用例文档模板（test-cases.md）

```markdown
# test-cases: <change 名>
## 故事 S1: <一句话用户故事>（锚 Requirement: <名>）
### 主链路（节拍串联）
| 步 | 动作 | 来源 Scenario | 期望 | 层 | 落点（测试/人工） |
| 1 | <用户动作> | <Scenario 标题> | <可判定预期> | <层> | <测试文件或人工：方式> |
### 变体走查
| # | 变体（组/条目） | 期望答案 | 层 | 落点 |
### 效果核对（触发问句④时）
- 触发原因 / 核对方法 / 量化结果 / 结论
### 继承与调整（涉及 MODIFIED/REMOVED Requirements 时必填，见问句⓪）
| 旧 Scenario | 处置 | 旧测试文件 | 动作 |
### 白盒附加（复杂档：状态机/算法/协议）
分支表 + 边界值清单 + 不适用划除留痕（判据主线程定，机械枚举可派子线程）
```

与归档对账的关系：主链路表的「来源 Scenario + 落点」列是设计层映射；机器对账仍以 tasks 验证节的 `| Scenario | 测试文件 |` 表为准（scenario-trace.sh 只扫 tasks.md）——两者指向同一批落点，不另起炉灶。

## 问句⓪：改契约了吗（回归走查，条件问句）

仅当本 change 的 delta specs 含 **MODIFIED / REMOVED Requirements** 时必答，纯新增 capability 豁免。

改契约时旧测试可能仍在断言旧契约——**跑绿 ≠ 对**。用 `bash scripts/test-assets.sh <capability>` 反查旧资产（主 specs 现状节拍 / archive 历史含 test-cases*.md 的 change / 历史 Scenario→测试文件映射），然后在 test-cases.md 填「继承与调整」表，逐行处置才算验收：

| 旧 Scenario | 处置 | 旧测试文件 | 动作 |
| --- | --- | --- | --- |
| <标题> | 继承 / 改语义 / 废止 | <路径> | 照跑（回归网） / 改断言 / 删除留痕 |

## 问句①：节拍全吗（被主链路表引用）

每个 Scenario 有测试落点了吗？用例文档主链路表把节拍逐条串进来，漏串的节拍一眼可见：

- 无自动化测试的 Scenario 显式映射「人工…」留痕（scenario-trace 既有约定，机器对账）
- 每个 SHALL NOT / 「不」/「拒绝」语句有负向 Scenario 对应（负向行为不测就是裸奔）
- 外部依赖（AI / 网络 / DB）失败路径有节拍：吞错降级还是阻断，spec 里要有答案

## 问句②：变体走查（五组固定清单）

把故事的输入 / 前置 / 状态换着走一遍，**每个变体都要有明确答案**（拒绝？空态？永不命中？），没想过的变体 = 产品决策缺口。固定条目制，不适用**划除留痕**（写一句为什么），防启发式随性：

| 组 | 固定条目 |
| --- | --- |
| 输入变体 | 空串 ｜ 纯空白（含全角空格 / tab）｜ 纯分隔符（单个 / 连续 / 开头 / 结尾）｜ 单 token ｜ 大小写 ｜ 特殊字符（正则元字符 / 引号 / emoji）｜ 超长输入 |
| 前置变体 | 空集（无数据）｜ 单元素 ｜ 重复元素 ｜ 越界 / 跨域引用（如不存在的 boardID）｜ 部分满足前置 |
| 时间窗口变体 | 边界两端（**当天算不算**、前后各一步）｜ 空窗口 ｜ 跨窗口 ｜ 时区 / 日期归一化 |
| 幂等变体 | 重复执行两次 ｜ 部分失败后重试 ｜ 并发（仅当声称线程安全） |
| 可用性变体 | 误输入反馈（提交非法输入界面说什么、已输内容丢不丢）｜ 空态 ｜ 错误态（依赖挂了用户看到什么）｜ 加载态 ｜ 超长文本展示 ｜ 重复提交 |

UI 故事必检前三项可用性变体（误输入反馈 / 空态 / 错误态），其余按交互形态取用。

## 问句③：层选对了吗（最便宜层原则）

每个测试落点选**能讲完这个故事的最便宜层**——下层测不完的故事才上贵层：

| 故事性质 | 层 | 载体 |
| --- | --- | --- |
| 纯逻辑（解析 / 判定 / 计算） | 函数单测 | `*_unit_test.go` / 纯函数 vitest |
| SQL / 迁移 / 约束 / 级联 | testcontainer PG | `testutil.SetupTestDB` 集成测试（repository 禁 SQLite） |
| HTTP 契约（参数 / 缺省 / 状态码） | handler 测试 | 轻量 handler test |
| 组件行为（单页内逻辑） | 组件测试 | Vitest + happy-dom |
| **完整交互故事（多步导航 / 表单流 / 前后端联动）** | **opencli 端到端** | 驱动真实 Chrome 走主链路（§5.3：交互流程验证主力） |

- **涉及前端交互流程的 change，主用户故事至少一个 opencli 端到端落点**（或「人工」留痕豁免）——组件测试管单页逻辑，完整故事要真实浏览器讲完。
- 视觉 / 布局验证派 k3 子代理截图，不混入交互验证（§5.3 工具分流）。

## 问句④：效果核对了吗

判定：故事的「得到什么」是否依赖测试断言之外的因素（数据覆盖率 / LLM 实际行为 / 外部服务）？是 → 测试绿灯后**必须**连真实库核对（呼应 backend/testing.md「绿灯 ≠ 功能有效」）。验证节加：

```markdown
### 效果核对
- 触发原因：效果依赖 <如 threads 摘要覆盖率 / LLM 判定质量>
- 核对方法：<跑什么 / 看什么页面 / 查什么数据>
- 量化结果：<命中率 / 覆盖率数字>
- 结论：达标交付 ｜ 瓶颈在<上游> ｜ 需调整预期
```

发现效果不达预期先定位瓶颈层（自己 vs 上游数据），量化数据摆给用户决策，不默默交付。

## 问句⑤：展示字段盘点了吗（改数据结构时的条件问句）

判定：本次改动的数据结构里，是否有**用户界面直接展示的字段**（标题 / 摘要 / 状态 / 计数 / 徽标文案）？是 → 逐个问：该字段的**来源语义**有没有 spec 锚（Requirement 声明它该取什么值）？

- 有锚 → 改来源走 MODIFIED Requirement + 问句⓪回归走查。
- 无锚 → 属「顺手实现」的隐式契约：先在本 change 的 delta spec 补 Requirement（声明来源语义）再改，禁止只改代码不补锚。

反例（2026-08 钉子户）：`daily_report_sections.cluster_label` 自 2026-07 lane 改制起实现为「命中话题 → 取话题 label」，spec 无锚 → 展示标题冻结在话题创建时的事件名上，后续每日新内容持续顶着过期旧标题两周无人发现，最终靠人工 SQL 取证定位（daily-report-section-title-decouple 才补锚）。测试防回归（声明过的行为改坏会叫），防不了从未声明的错误行为——展示字段的 spec 声明是唯一拦截点。

## 验收措辞规范（可机械判定）

验收必须落成三形态之一：**命令+期望**（`go test ./internal/topicgraph/service -run TestX → PASS`）、**文件存在**（`新增 xxx_test.go`）、**人工留痕**（`人工：验证方式说明`——光写「人工」不算）。

**禁用词表**（spec-gate 检查⑤扫描此表；改此表必同步 `.pi/extensions/lib/test-case-gate.ts` 常量与 `.pi/extensions/spec-gate.ts` 引用，双向声明缺一不可）：

| 违例措辞 | 问题 | 改法 |
| --- | --- | --- |
| 「单测覆盖」（不带用例清单） | 覆盖了啥全靠脑补 | 「单测覆盖：(1)空串 (2)纯\| …」或引 test-cases.md |
| 「测试 PASS」（不带命令） | 哪个测试？ | 带完整命令 |
| 「正确 / 合理 / 完整 / 等 / 之类」单独出现 | 不可判定 | 封闭式列举或量化 |
| 纯函数任务提「SQLite」 | 分层错配（⑤b） | 「单元测试（无 DB）」 |
| proposal 未声明复杂度（缺 `<!-- complexity: complex\|simple -->`） | 声明制下复杂度是设计阶段判断，应落机器可读声明 | proposal 头补声明 |
| 声明 `complex` 但 change 目录无 test-cases*.md | 声明复杂档漏白盒（⑤a 强违例，动工入口 steer + 归档 warn 双提醒） | 补文档或改声明 |
| 声明 `simple` 但任务行命中复杂档关键词（算法 / 状态机 / 解析 / 协议）且无 test-cases*.md | 声明与任务措辞矛盾（⑤a 反向质询） | 改声明为 complex 并补文档，或调整措辞并确非复杂档 |
| 未声明 + 任务行命中复杂档关键词且无 test-cases*.md | 可能复杂档漏白盒（⑤a 兜底，entry-gate 动工时 steer 提醒） | 补声明；确复杂则补文档 |

## 白盒分支表（复杂档附加）

复杂档（状态机 ≥3 状态 / 复杂算法 / 多模块协议）在用例文档的「白盒附加」节补分支表——**附加件非主角**，故事层测不到的分支爆炸才需要（沿 case-first-testing 义务；断言判据主线程定，机械枚举可派子线程）：

```markdown
### 白盒附加
## 分支表
| # | 条件/分支 | 输入 | 期望 | 测试用例名 |
## 边界值清单
| 变量 | 边界值 | 期望 | 测试用例名 |
## 不适用划除（留痕）
- <条目>：不适用（<一句理由>）
```

## JIT 注入摘要

> 速查版，权威全文见本文档主体，**改主体必同步本节**（≤3KB 硬约束）。

**单元**：测试单元 = 一个 Requirement 的用户故事，**由 change 目录 test-cases.md 串成完整故事**（spec Scenario 只是断言片段）：主链路表串节拍（步/动作/来源 Scenario/期望/层/落点）+ 变体走查 + 效果核对 + 白盒附加。涉及行为的 change 必须有 test-cases.md（纯文档/工具链豁免）。双轨：方法单测允许（快反馈），交付账本在故事层——故事绿才算交付。

**五问句**：
0. **⓪ 改契约了吗**（仅 MODIFIED/REMOVED Requirements 时）——旧测试可能仍断言旧契约，跑绿≠对：`bash scripts/test-assets.sh <capability>` 反查旧资产，test-cases.md 填「继承与调整」表（旧Scenario×处置×旧测试×动作）逐行处置
1. **节拍全吗**——每 Scenario 有落点；SHALL NOT 有负向节拍；外部依赖失败有答案；无自动化→「人工…」留痕
2. **变体走查**——五组固定清单，每变体有明确答案，不适用划除留痕：
   - 输入：空串｜纯空白(全角/tab)｜纯分隔符(单/连/首/尾)｜单token｜大小写｜特殊字符｜超长
   - 前置：空集｜单元素｜重复｜越界引用｜部分满足
   - 时间窗口：边界两端(当天算不算)｜空窗口｜跨窗口｜归一化
   - 幂等：重复执行｜部分失败重试｜并发(仅当声称线程安全)
   - 可用性(UI必检前三)：误输入反馈｜空态｜错误态｜加载态｜超长文本｜重复提交
3. **层选对了吗**——最便宜层：纯逻辑→函数单测｜SQL/迁移→testcontainer PG(repository禁SQLite)｜HTTP→handler｜组件→Vitest｜**完整交互故事→opencli 端到端(前端交互 change 主链路至少一个 opencli 落点或人工豁免)**；视觉派 k3 截图
4. **效果核对了吗**——效果依赖断言外因素(数据覆盖率/LLM行为)→真库量化核对：触发原因/方法/量化结果/结论
5. **展示字段盘点了吗**（改数据结构时）——含用户可见字段(标题/摘要/状态/计数/徽标)→**来源语义**须有 spec 锚；有锚改走 MODIFIED+⓪，无锚先补 Requirement 再改（隐式契约=测试盲区，详见主体⑤）

**验收措辞**：三形态之一——命令+期望｜文件存在｜「人工：验证方式」。黑名单：「单测覆盖」无清单｜「PASS」无命令｜「正确/合理/完整/等/之类」单独出现｜纯函数×SQLite（⑤b）｜复杂度未声明｜声明 complex 缺 test-cases*.md（⑤a 强违例）｜simple/未声明+任务行命中 ⑤a 关键词（算法/状态机/解析/协议）。词表不扩容（主信号=声明，词表仅兜底）。

**白盒附加**：复杂档（状态机/算法/协议）在 test-cases.md 白盒附加节出分支表+边界值+不适用划除留痕（判据主线程定）——附加件非主角。
