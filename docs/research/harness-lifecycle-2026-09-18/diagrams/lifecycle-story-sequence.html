一次开发生命周期：10 个扩展角色谁在何时出手

图 1 全景把扩展层画成一整条泳道——这张图把那条泳道拆开演。四幕连续剧，每一幕是一张独立的顺序图（每幕至多 5 条生命线），10 个扩展角色全员登台：谁挂哪个钩子、说了什么话、软提醒还是硬拦截，消息标签就是台词。人类只有两个角色：用户（你）与主线程，子线程是派出去干活的 Agent。

第 1 幕 · 开工：规矩先进脑子① 探索 → ② 提案 → ③ 编排

此时还没绑 change，constraint-injection 只给一份「约束索引」当书签——等你写完 proposal 头部的两个声明（ui-impact / constraint-domains）、切入 implementation 档，声明域的红线才整段进 system prompt。harness-telemetry 全程默默把事实写进 events.db（constraint.inject / mode.set / gate.check / patrol.check / policy.decision / edit.map / spill.write / session.start / session.rollup / subagent.* / pin.write），fail-safe 不干预。

第 2 幕 · 派发：两道硬门④ 派发

主线程把实现任务派给子线程，这一步埋着整个体系仅有的三道硬拦截中的两道：quota-gate 先查供应商额度（5h/周窗口 <10% 或余额 <¥1 就 block），ui-design-gate 再查 major 原型审批。门禁每次检查都重读磁盘——第 1 幕用户批准过，这里直接放行。

第 3 幕 · 写码：四个护卫轮值⑤ 实现 → ⑥ 迭代 → ⑦ review

子线程开写。这一幕没有硬拦截，全是软提醒与自动整理：test-scope-guard 拦全量测试、tool-output-spill 落盘超大输出、entry-gate 催补白盒用例文档；只有 quality-gate 的 turn_end 增量门禁带牙齿——[回归] 必须修，[中间态] 可以继续推进，归档前全绿的总要求不变。

第 4 幕 · 归档与收尾：最后的关卡⑧ 验收归档 → ⑨ 溯源 retro · 会话结束

主线程自检后执行 openspec archive，spec-gate 做五项机器检查——任一失败就是一份修复清单，全过才放行归档。会话结束时 dev-process-guard 清掉泄漏的 dev 进程组；harness-retro.sh 只读消费账本产出六段聚类报告（门禁失败 / 回归翻转 / 自身故障 / 软提醒失效 / 重复热点 / 注入面健康 + 效能看板），改进项走新 change——故事回到第 1 幕。
